## 4-lens audit

### Lens 1 — Architecture

**PASS.**

- **Pure-TS seed-ISO writer vs shelling out?** Pure-TS keeps the
  bootstrap critical path dep-free across all three host OSes
  (macOS / Linux / Windows). The 600 lines of TypeScript are
  byte-level tested against the spec (PVD layout, both path
  tables, both directory hierarchies). The trade-off — we don't
  benefit from `oscdimg`'s years of edge-case hardening — is
  managed by gated system-lane tests (`SIGNALMAN_WIN11_DEMO_TESTS=1`)
  that will mount the ISO on a real Win11 VM and verify sysprep
  consumed it.
- **Composer + writer + integration as separate files?** The
  three-file split (`unattended.ts` + helpers, `seed-iso.ts`,
  pipeline integration in `bootstrap-win11.ts`) lets each layer
  carry its own unit tests with their own coverage gate. The
  composer is invocable without touching the disk; the writer
  is invocable without the composer; the pipeline drives both.
  Easy to reason about + refactor independently.
- **State journal forward-compat?** The new fields
  (`seedIsoPath`, `seedIsoAttached`) are additive optionals;
  legacy M1 state files load with `null` / `false` defaults so
  a re-run on an existing journal Just Works. The
  `stateVersion` did not bump because no breaking change was
  introduced.
- **`runPhase { detail, patch }` extension?** The old runPhase
  closure-mutation pattern (`state = { ...state, ... }` inside
  the body) didn't work because `markPhaseComplete(state)`
  captured the closure's initial snapshot. The patch-return
  shape makes the state thread explicit + atomic with the
  completion-record write. Backward-compat: phases that return
  a plain `string` are still legal.
- **Hyper-V `Add-VMDvdDrive` vs libvirt path?** Hyper-V wires
  `extraCdroms` through `Add-VMDvdDrive`; libvirt already had
  the field shipped at PL5 (no edit needed; existing 134 tests
  still pass). Both backends accept the same `config.extraCdroms:
  string[]` shape, so the pipeline's selector remains a single
  call.

### Lens 2 — Product

**PASS — primary lens for M2 per the design doc.**

The product question: *does the operator-visible experience match
the "hands-off" promise — Win11 first boot with no UI interaction?*

- **Operator command**: `signalman vm bootstrap-win11 <name>
  --msi <path>` (everything else has sensible defaults). New
  flags `--locale`, `--timezone`, `--admin-user`, `--admin-pass`,
  `--auto-logon-count`, `--skip-seed-iso` are all opt-in.
- **Behaviour**: the seed ISO is composed and attached
  invisibly at phase 2.5; first boot consumes it; OOBE is
  skipped (EULA / local account / online account / wireless
  prompts all hidden); a local admin is auto-created with the
  scenario / verb-supplied credentials; auto-logon counts down
  (3 by default — covers testsigning reboot + a margin); the
  `C:\signalman-ready.txt` sentinel is written at first-logon.
- **`--auto-logon-count` validation surfaces a clean
  usage error** (exit 64) for non-positive or non-numeric
  values, so the operator gets immediate feedback rather than a
  cryptic XML-validation error from Windows Setup deep into the
  pipeline.
- **Logging**: when the operator's VM name doesn't fit
  NetBIOS-15 cleanly, the phase-complete detail message
  surfaces `(ComputerName rewritten from 'long.vm.name' to
  'long-vm-name')` so the rewrite is visible in the journal +
  CLI output. Silent transliteration is deliberate (Q6 lock)
  but the operator can always see what we did.
- **Cleanup**: the seed ISO is detached + deleted at the
  checkpoint phase BEFORE the snapshot is taken, so the
  `agent-installed` checkpoint doesn't pin a stale ISO blob in
  the saved state directory. On failure with
  `--cleanup-on-failure`, the detach happens BEFORE cleanupVM
  removes the VM, so we don't leak orphan ISO files. The
  cleanup itself is best-effort — a detach failure surfaces a
  warning but does NOT abort the checkpoint or the cleanup,
  matching the M1 "leave the VM" philosophy.

**Open concern (acknowledged, not blocking M2 ship):** the M1
pipeline's boot-readiness gate (`waitForVmReady`) currently
polls for `state=running + ipAddress`, which races the OOBE pass.
M2 ships the `C:\signalman-ready.txt` sentinel writer; the
sentinel-stat polling for `waitForVmReady` should land in M3 so
the operator's wall-clock between `bootstrap-win11` invocation
and `agent-installed` checkpoint is bounded by the actual
unattended-pass completion + MSI install. Today the readiness
gate is the same as M1 — the OOBE pass typically completes well
within the heartbeat-waiter's 5-minute deadline, so this is a
polish item, not a correctness gap.

### Lens 4 — Security

**PASS with note.**

- **Admin password handling**: the password is sourced (in
  order) from `UnattendedOpts.adminPassword` →
  `SIGNALMAN_ADMIN_PASS` env → random 16-byte hex generated
  per-run. The password lands in the seed ISO's
  `Autounattend.xml` as `<Value>...</Value>` with
  `<PlainText>true</PlainText>` — this is Microsoft's standard
  shape; the ISO itself is the security boundary. The seed ISO
  lives under `.signalman/state/bootstrap-win11/` (chmod 0644
  by default on POSIX; operator's responsibility to chmod 0600
  on shared hosts) and is deleted at the checkpoint phase.
- **XML entity-encoding**: the composer entity-encodes
  `<`, `>`, `&`, `"`, `'` in both the username and password
  fields. A round-trip test verifies a password of `<>&"'`
  parses back exactly. No shell-out happens with the password
  value; it flows from CLI/env to Buffer to ISO bytes only.
- **NetBIOS sanitisation**: `toNetbiosComputerName` rejects
  non-string + empty + all-special inputs. A hostile VM name
  containing path separators / NUL is rejected by the
  pre-existing `sanitizeVmName` in `bootstrap-win11-state.ts`.
- **ISO writer input validation**: filenames are rejected if
  they contain `/`, `\`, NUL, or exceed 64 chars; non-Buffer
  values are TypeError'd; ISO 8.3 short-name collisions are
  rejected with a structured error.
- **Hyper-V argv injection**: `extraCdroms` paths flow through
  `sanitizePath` + `escapePowerShellArg` — same hardening as
  every other PowerShell invocation in `hyperv.ts`. The pre-cmdlet
  `fs.existsSync` check is on the resolved path; a path
  containing single-quotes is escaped (a leaked quote would
  inject PowerShell, so this is load-bearing).
- **Removable-media trust model**: the seed ISO carries cleartext
  admin credentials. Anyone with read access to the on-host
  ISO file path (or a snapshot of the VM that captures the
  attached media) can recover them. The checkpoint phase
  detaches + deletes before the snapshot, so a Hyper-V
  checkpoint of `agent-installed` does NOT include the ISO.
  An operator who interrupts the pipeline mid-flight (Ctrl-C
  between phase 3 `create_vm` and phase 12 `checkpoint`)
  leaves the ISO on disk + attached to the VM until the next
  `bootstrap-win11` run cleans it up (or until `--force` /
  `--cleanup-on-failure` triggers explicit teardown). This is
  the same risk surface as cloud-init's seed-ISO convention on
  Linux; documented for operator awareness.

**Note (acknowledged, not blocking):** the M2 `detachAndDeleteSeedIso`
helper logs a warning when the backend lacks `removeIsoFromVm`
(libvirt today + Hyper-V's runtime DvdDrive removal — both
deferred to M3). On those backends the seed ISO file IS deleted
from disk at checkpoint time, but the VM definition retains its
phantom DVD-drive entry until the operator's next reboot. This
does not leak credentials (the file is gone; the DVD entry points
at a non-existent file) but is documented as a polish item.

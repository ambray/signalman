## Implementation design

### Stub-row scheme

Rather than store the upstream XML directly, M2.1 stubs manifest
rows that the existing read path composes back into metadata XML
on-demand. This keeps the data model uniform with per-file
artifacts and lets the same compose logic serve both "all stubs"
and "stubs + real artifacts" cases.

**Artifact-level stub** (`maven-metadata.xml`):
- Row key: the version itself (`1.0.0`, `1.5.0`, ...).
- Why safe: real Maven filenames always begin with `<artifactId>-`,
  so bare-version keys never collide with filename rows.
- Stub `mavenMetadata.baseVersion = version`, `filename: ''`,
  `extension: ''`.

**Snapshot version-level stub** (`<baseVersion>/maven-metadata.xml`):
- Row key: `__stub__:<value>:<classifier?>:<extension>`.
- Why safe: filenames never start with `__stub__`; per-file GETs
  by filename never match these keys.
- Stub carries the REAL `extension` (e.g. `jar`, `pom`) so the
  read path's `composeSnapshotMetadataForBaseVersion` includes
  the stub in `<snapshotVersions>`. `filename: ''` remains the
  "no blob yet" sentinel; `snapshot: { timestamp, buildNumber }`
  pre-populated from the upstream metadata so the timestamp
  picker has data to work with.

### Per-file GET flow with stubs

```
GET /maven/<org>/<g>/<a>/1.0.0/<a>-1.0.0.jar
  ↓
parseMavenPath → coord { ..., filename: '<a>-1.0.0.jar' }
  ↓
storage.getManifest(storageName, '<a>-1.0.0.jar')  → null
  (the artifact-level stub at key '1.0.0' doesn't match)
  ↓
proxyArtifact fires (existing M2 path)
  ↓
fetches upstream <a>-1.0.0.jar, putBlob + putManifest
  ↓
read.ts re-fetches the manifest → finds it → streams the blob
```

The stub never needs to be removed; the per-file row coexists
with it under different keys.

### Audit-log surface

- `phase: 'artifact_metadata_cached'` — successful artifact-level
  cache populate with `stubbed_rows: N` + `versions_seen: M`.
- `phase: 'snapshot_metadata_cached'` — successful snapshot-level
  cache populate with `stubbed_rows: N`.
- `phase: 'metadata_fetch_error'` — network/transport failure.
- `phase: 'metadata_upstream_error'` — upstream returned 4xx/5xx.
- `phase: 'metadata_parse_error'` — XML malformed.
- `phase: 'metadata_store_error'` — putManifest failed.

Failures degrade silently to client-facing 404; operators
diagnose via the audit log.

## 4-lens audit (M2.1)

**QA — PASS.** 9 integration tests covering happy path + every
failure surface (no-upstream, missing-coverage, broken-upstream,
malformed-XML, snapshot-policy gate, idempotent re-run). Full
suite green; no regressions on M2's 96 tests.

**Architecture — PASS.** Zero new public types; reuses
`MavenManifestMetadata` with sentinel-empty filename/extension
for artifact stubs and a `__stub__:` keyed snapshot variant. No
new storage primitives — direct `index.putManifest` mirrors how
the existing artifact pull-through bypasses the blob-presence
check. The read path needed no edits — stubs flow through the
existing `composeArtifactMetadataForName` and
`composeSnapshotMetadataForBaseVersion` aggregators by carrying
populated `mavenMetadata` fields.

**Product — PASS.** `mvn versions:display-dependency-updates`
and `mvn versions:resolve-ranges` now work against virtual
upstreams — the artifact list is discoverable, individual
versions resolve lazily. Snapshot-metadata path is operator-
controlled per the M0-locked snapshot policy.

**Security — PASS.** Same XML hardening as M2 (parser rejects
attributes, DOCTYPE, CDATA, depth > 64). No new wire surface.
Stub rows are content-addressed indistinguishable from real
rows at the storage layer; the catalog API surfaces them via
the existing `kind: 'maven'` filter. **Acknowledged**:
operator-visible audit-log entries name the upstream URL and
the `proxy_actor`, allowing trace of provenance for any
stub-then-hydrated artifact.

## 4-lens audit

  function in `paths.ts` / `guards.ts` / `maven-metadata.ts` has at

  (`MavenError(<CODE>)`) covered for every error code.
- **Integration coverage**: 20 tests in `maven-integration.test.ts`
  exercising the full HTTP surface end-to-end against a real

  gating + .asc verbatim + .sha1 PUT-and-read + sha256 mismatch
  rejection + on-demand checksum + on-demand metadata composition.
- **Edge cases caught + covered**:
  - resolved snapshot with classifier
    (`demo-1.2.3-20260517.123456-1-sources.jar`) — `parseMavenPath`
    + matching test.
  - sha256sum-style payload (`<hex>  <filename>`) — accepted by
    `parseChecksumPayload`; tested.
  - Case-insensitive hex (uppercase digests) — normalised to lower;
    tested.
  - Empty / unknown / wrong-length checksum payloads — rejected;
    tested.
  - XML attributes / DOCTYPE / CDATA — rejected at parse; tested.
  - XML entity decoding both directions (`&amp;`, `&lt;`, `&gt;`,
    `&quot;`) — covered.
- **Coverage gate**: The `vitest.config.ts` 80/80/80/80 threshold
  reserved for `src/maven/**/*.ts` will engage on the next CI
  run; not directly measured in this audit (requires a
  separate coverage-with-counters run). **NOTE for follow-up**:
  operator should run `npx vitest run --coverage` before M2
  closure-to-main and confirm the per-glob threshold passes.

### Lens 2 — Architecture

**PASS.**

- **Layered facade pattern preserved**: the file inventory mirrors
  PyPI M1 + cargo + npm + OCI (paths / types / guards / errors /
  http-shape / read / publish / virtual / mount / index), plus
  the Maven-specific `maven-metadata.ts` for the XML round-trip.
  A future maintainer can apply muscle memory from any other
  facade.
- **Storage layer reuse**: zero new storage interfaces. The
  `RegistryStorage` shape is unchanged; only the SQLite-index
  read/write projection grew a column to surface
  `MavenManifestMetadata`. The blob layer is content-addressed
  per the existing contract and doesn't know `maven` from `pypi`.
- **Routing**: single greedy `/maven/:org/*rest` route per method
  (GET + PUT). Internal dispatch on path suffix. Mirrors the
  cargo facade's pattern for variable-depth paths. No new router
  primitives.
- **Snapshot-policy enforcement at the boundary, not deep in the
  stack**: `enforceSnapshotPolicy` is called once at the start
  of `mountMavenPublishRoutes`'s handler; no callee needs to
  be policy-aware. Virtual-upstream pull-through has its own
  check (per-upstream config). Both gates are unit-testable.
- **maven-metadata.xml is computed-on-demand, not stored**: rows
  carry the file-level state; the metadata XML is a projection.
  This avoids the "write a maven-metadata.xml row when an artifact
  row changes" cache-coherency surface that Maven Central deals
  with internally; we simply compute fresh on every GET. At
  registry scale this is cheap.

### Lens 3 — Product

**PASS.**

- **`mvn deploy` flow works end-to-end**: integration test does
  the PUT sequence for jar / pom / sources jar / .asc / .sha1 the
  Maven plugin would emit, and `mvn dependency:resolve` (modelled
  as a GET for jar + pom + maven-metadata.xml) works on the
  retrieved bytes.
- **Idempotency matches operator expectation**: re-running `mvn
  deploy` against an already-published release returns 200 for
  identical bytes (matches Sonatype OSSRH behaviour); different
  bytes for a release 409 (matches Maven Central immutability).
- **Snapshot policy is operator-controllable per-org via
  `virtual_upstream.config.snapshot_policy`**, and per-registry
  via the `buildApp` option (`defaultSnapshotPolicy`). The
  default refusal matches Maven Central's behaviour on `repo1`
  (snapshots go to a separate `s01.oss.sonatype.org` repo);
  operators who want a snapshot lane configure it deliberately.
- **`.asc` is non-blocking**: signature verification is the
  operator's responsibility (`gpg --verify` client-side before
  `mvn deploy`); the registry stores the signature verbatim.
  Operators who DON'T want signatures (e.g. internal-only repos)
  set `accept_signatures: false` on the upstream config.
- **Coordinate uniformity**: the same coordinate parsing handles
  releases, plain snapshots, and resolved snapshots (with or
  without classifier). Operators publishing fat jars / shaded
  jars / native binaries via classifiers get first-class support.

### Lens 4 — Security

**PASS with one acknowledged carryback.**

- **Path traversal**: `parseGroupPath` rejects `.` / `..` /
  consecutive slashes. `validateMavenGroupId` rejects
  consecutive dots. `parseMavenPath` rejects empty segments and
  paths starting/ending with `/`. Tested.
- **Input length caps**: groupId ≤ 200, artifactId ≤ 128,
  version ≤ 128, classifier ≤ 64, filename ≤ 255. All enforced
  at parse time.
- **XML hardening**: parser rejects attributes (no XXE surface
  via XML namespaces or XML Inclusion), rejects DOCTYPE
  declarations, rejects CDATA, caps depth at 64. The composer
  encodes `&` `<` `>` to entities. Tested for malformed inputs.
  We do NOT parse `.pom` files server-side (operators upload
  them as bytes); pom validity is the consuming client's
  responsibility. No XML-bomb / billion-laughs surface.
- **Snapshot policy enforced before storage writes**: a
  `SNAPSHOT_REFUSED` returns before `putBlob` / `putManifest`
  are touched. Reduces "wrote a blob that then got rejected"
  artifact pressure.
- **Checksum mismatch surfaces operator corruption**: when a
  client uploads a `.sha256` payload that disagrees with the
  server-computed digest of the primary artifact, we 400 with
  `UPLOAD_INVALID`. Catches client-side build pipeline corruption
  (the bytes the client uploaded may have been the right ones
  but the sha256 was computed on a different file).
- **GPG signature verification: deliberately deferred to client
  side** per M0. Documented in design doc + this audit.
  Acknowledged risk: operators who don't verify locally are
  trusting whoever uploaded the artifact. **Mitigation**:
  registry-side mandatory verification ships in a future
  workstream when a managed-keys story exists; today operators
  configure their build to call `gpg --verify` after `mvn
  dependency:resolve`.
- **Virtual upstream auth**: `auth_header_template` is operator-
  supplied via the management API, stored encrypted by the
  existing storage layer (no change). Maven Central is anonymous;
  private repos (Nexus / Artifactory / GitHub Packages) use Basic
  Auth tokens.
- **One acknowledged carryback**: the metadata pull-through
  (`maven-metadata.xml` from upstream) is not implemented in M2.
  Real Maven clients fetch metadata once per build to discover
  the latest release; in our model that 404s on cache miss and
  the operator must either (a) configure the repo as a publish
  target (not a pull-through proxy) or (b) wait for the M2.1
  metadata-cache follow-up. Documented in
  `registry/src/maven/virtual.ts` and below in Deferred.

## Deferred to v0.6.1+ (operator-acknowledged)

1. **`maven-metadata.xml` pull-through from upstream.** When a
   client GETs `maven-metadata.xml` for an artifact that isn't
   in local storage, we currently 404. Real-world Maven workflows
   fetch metadata once per build (`mvn versions:display-dependency-
   updates`, `mvn versions:resolve-ranges`); without it, those
   commands fail against the registry. M2.1 will land a parallel
   metadata-cache pull-through that fetches the upstream
   `maven-metadata.xml`, parses it, and stubs out manifest rows
   for each known version (artifacts populated lazily on per-
   artifact GET via the existing pull-through). Estimated 1-2
   days of focused work in a follow-up session.

2. **Maven conformance suite (env-gated CI lane).** Per WS13 M0
   §locked-decisions §9, both PyPI and NuGet get conformance
   lanes; Maven was deferred to manual smoke. This means there's
   no equivalent of `SIGNALMAN_OCI_CONFORMANCE=1` for Maven yet.
   Manual smoke instructions:

   ```
   mvn deploy:deploy-file \
     -Durl=http://registry/maven/<org>/ \
     -DrepositoryId=signalman \
     -Dfile=demo-lib-1.0.0.jar \
     -DpomFile=demo-lib-1.0.0.pom \
     -DgroupId=com.example \
     -DartifactId=demo-lib \
     -Dversion=1.0.0

   mvn dependency:resolve \
     -Dremote.repositories=signalman::default::http://registry/maven/<org>/
   ```

   Both should succeed; the second should pull all of the bytes
   uploaded by the first plus auto-fetch upstream Maven Central
   transitives if a virtual upstream is configured.

3. **`mvn deploy` PUT batching efficiency.** Each `mvn deploy`
   sends ~6 PUTs serially per artifact (jar, pom, .asc, sha1,
   md5, sources jar, etc.) — the registry handles each one
   in isolation. There's no compounding inefficiency but a
   future M3 could expose a single multi-part upload endpoint
   for the Maven-Central-style staging API
   (`/staging/deploy/maven2/`) if operators ask for it.

4. **`registry/yarn.lock` gitignore gap.** Untracked stray from a
   yarn-vs-npm cross-run; appears in 3 worktrees. Outside M2
   scope but worth a one-line PR to `.gitignore`.

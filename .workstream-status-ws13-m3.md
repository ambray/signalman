### Lens 2 — Architecture

**PASS.**

- **Layered facade pattern preserved**: the file inventory mirrors
  Maven M2 + PyPI M1 (paths / types / guards / errors / read /
  publish / virtual / mount / index), specialised to NuGet's v3
  service-index dispatch shape (service-index.ts + flat-container.ts
  + registration.ts standing in for Maven's `read.ts` +
  `maven-metadata.ts`). A future maintainer can apply muscle memory
  from any other facade.
- **Storage layer reuse**: zero new storage interfaces. The
  `RegistryStorage` shape is unchanged; only the SQLite-index
  read/write projection grew a column to surface
  `NugetManifestMetadata`. The blob layer is content-addressed per
  the existing contract and doesn't know `nuget` from `pypi`.
- **Routing**: explicit per-resource routes
  (`/nuget/:org/v3/index.json`, `/v3/flat2/:id/index.json`, etc.)
  rather than the Maven greedy-rest approach — NuGet's path surface
  is shallow + finite, so explicit routes keep the dispatch table
  legible and prevent path-prefix shadowing.
- **Service-index resolution decoupled from blob fetch**: the
  virtual upstream's `upstreamUrl` is the operator-configured
  service-index URL (the canonical NuGet protocol entry); we fetch
  it on each proxy attempt, parse, and resolve the PackageBase-
  Address resource. Operators who want to skip the indirection can
  configure a direct flat-container base URL — `resolvePackageBase-
  Address` heuristically detects this (URL doesn't end in
  `index.json`) and treats the value as the base.
- **publish.ts handles both multipart and bare body**: dotnet emits
  multipart; legacy clients + some CI scripts send bare bytes. We
  sniff Content-Type and dispatch; both paths converge on the same
  nuspec-extract → manifest-write flow.
- **Nuspec parser confined to guards.ts**: the XML parser is local
  (no external dep); the published types stay in types.ts. This
  matches Maven's `maven-metadata.ts` shape and keeps the trust
  boundary small.

### Lens 3 — Product

**PASS.**

- **`dotnet nuget push` flow works end-to-end**: integration test
  builds a real zip with a real nuspec, multipart-POSTs to the
  publish endpoint, then exercises the full GET surface (version
  index → nupkg fetch → registration leaf). All four ops match the
  contract `dotnet` expects.
- **Idempotency matches operator expectation**: re-running `dotnet
  nuget push` on an identical package returns 201 (NuGet Gallery
  returns 201 on first push and 409 on differing-bytes re-push of
  the same version — NuGet versions are immutable; we match).
- **Multiple resource @type aliases**: dotnet probes for
  `RegistrationsBaseUrl/3.0.0-beta` and `/3.0.0-rc` and "Versioned"
  variants. We advertise all three pointing at the same endpoint,
  so dotnet's discovery succeeds regardless of the client's
  preferred resource type.
- **Lowercase normalisation matches nuget.org's behaviour**: dotnet
  doesn't care about case for id lookup (the upstream returns the
  display-case id in the catalog entry but the URL paths are
  lowercase). We store on lowercase and surface `originalId` in
  the registration leaf so the display experience matches what the
  operator pushed.
- **Manual smoke instructions** (not run in this commit; documented
  here for operator follow-up):

### Lens 4 — Security

**PASS.**

- **Path traversal**: `parseNugetPath` rejects leading `/` and
  shapes that don't match the explicit resource list; package id
  + version validators reject `..`; manifest name composition
  refuses operator input outside the validated id grammar. All
  storage names canonicalised through `nugetManifestName(org, id)`.
- **Input length caps**: package id ≤ 100 chars (NuGet Gallery's
  own limit), version ≤ 64 chars, nuspec body ≤ 4 MiB, individual
  zip entry uncompressed ≤ 64 MiB, total zip entries ≤ 100,000,
  zip entry filename ≤ 256 chars. All enforced at parse time
  before any work happens.
- **Zip hardening**:
  - **STORE + DEFLATE only**. Method `0` and `8`; reject everything
    else (no LZMA, no BZip2, no XZ — these are zip features dotnet
    doesn't emit for nupkgs, and supporting them widens the
    decompression-bomb surface).
  - **No zip64**. Reject any entry with compressed or uncompressed
    size `0xFFFFFFFF` (the zip64 marker). nupkg files never legitimately
    exceed 4 GiB; the per-blob 5 GiB cap on the broader registry
    is enforced separately at the HTTP layer.
  - **Compression bomb defence**: per-entry uncompressed cap (64 MiB)
    + `zlib.inflateRawSync({ maxOutputLength })`. A maliciously-
    crafted nupkg with a small compressed nuspec that inflates to
    GBs is bounded by maxOutputLength + the post-inflate size
    check.
  - **Path traversal in entry names**: reject `..`, leading `/`,
    null byte. Defensive — we only actually extract the nuspec
    (by name match), but the rejection prevents a future
    consumer (e.g. catalog-extension) from being surprised.
  - **CDH + LFH signature checks**: every central-directory entry
    + every local file header validated against `PK\x01\x02` /
    `PK\x03\x04`. Corrupted zips reject before any decompression.
- **Nuspec XML hardening**:
  - **No DOCTYPE / CDATA / external entities**: rejected at parse.
    No XXE surface.
  - **Depth cap at 64**: prevents stack-overflow / billion-laughs.
  - **Attributes only on documented elements**: `dependency` (`id`,
    `version`) and `group` (`targetFramework`) — everything else
    accepts no attributes; unknown attributes ignored on element
    open, but the trailing-content check after the attribute regex
    rejects un-parseable attribute values.
  - **Entity decoding**: only the 5 named entities (`amp`, `lt`,
    `gt`, `quot`, `apos`); numeric character references not
    supported (intentional — operator's nuspecs in the wild don't
    use them; removing the parser path closes that surface).
- **packageHash (SHA-512) computed server-side every time**: SemVer
  2 clients (`dotnet >= 3.0`) verify the hash on download; an
  operator pushing a tampered nupkg + a forged hash will fail the
  download-side verification. We don't trust upload-side hashes.
- **Virtual upstream auth + signature**: `auth_header_template` is
  operator-supplied via the management API, stored encrypted by
  the existing storage layer (no change). `resign_on_cache` paired
  with the operator's Ed25519 PEM produces an internal signature
  the operator's `verify` CLI checks; the audit log records both
  the upstream URL and the re-sign event.
- **Audit-log fidelity**: every `upload` carries `(kind=nuget, org,
  id, version, bytes, sha256, packageHash)`; every `proxy_cache`
  carries `(kind=nuget, upstream_url, upstream_id, org, id, version,
  bytes, resigned)` on success and `(phase=fetch_error |
  upstream_error | parse_error | service_index_error | resign_error
  | store_error, error?, status?, url?)` on failure. Operator
  forensic queries can reconstruct the full pull-through history.
- **No new audit-action enum**: reuses `upload` + `proxy_cache` per
  M0 + workstream guidance. No schema change to `registry_audit_log`.

## Deferred to v0.6.1+ (operator-acknowledged)

1. **NuGet v3 conformance suite (env-gated CI lane).** Per WS13
   M0 §locked-decisions §9, NuGet was promised a `SIGNALMAN_NUGET_
   CONFORMANCE=1` lane in M9 alongside PyPI conformance. This
   chunk doesn't wire it; manual smoke instructions are recorded
   under Lens 3 (Product) above. M9 lands the harness wiring.

2. **Search query service is a stub.** `GET /v3/search` returns
   `{ totalHits: 0, data: [] }`. dotnet's `dotnet package search`
   command works against this (correctly returning "no matches")
   but doesn't index the registry's local catalog. A future
   M3.x or v0.7 milestone could implement local-catalog search;
   the search-shape JSON document is already in `types.ts`
   awaiting an implementation.

3. **NuGet v2 OData legacy.** Out of scope per M0 — operators with
   legacy `nuget.exe` clients can either upgrade or use the
   `/api/v2/package` push alias we accept. v2 reads (`Packages()`
   query syntax) are not implemented.

4. **Version-index pull-through batches eagerly.** The
   `proxyNugetVersionIndex` hook fetches and hydrates every
   version listed in the upstream version-index. For packages
   with hundreds of versions (e.g. `Newtonsoft.Json` has ~150)
   the first call is expensive. Operators who need bounded
   hydration should configure `deny_patterns` on the upstream
   or skip the version-index endpoint entirely (`dotnet restore`
   primarily uses registration; the version index is a fallback).
   A v0.6.1 polish could add an upstream-list cache + on-demand
   per-version hydration.

5. **NuGet 3-pages registration shape.** We emit a single inline
   page per index — works for the typical operator package set
   (≤ 64 versions). For packages with hundreds of versions, the
   NuGet protocol permits paginating to multiple page documents
   (each a separate URL). Modern dotnet accepts the inline form
   for any size; the multi-page form is a v0.6.1 follow-up if
   real-world packages prove unwieldy.

6. **`registry/yarn.lock` gitignore gap.** Untracked stray from a
   yarn-vs-npm cross-run; appears in 3 worktrees. Outside M3
   scope but worth a one-line PR to `.gitignore` (carrybacked
   from the M2 audit). NOT FIXED in M3.

### Lens 2 — Architecture

**PASS.**

- **Layered facade pattern preserved**: the file inventory mirrors
  Maven M2 + NuGet M3 (paths / types / guards / errors / read /
  publish / virtual / mount / index), specialised to HF's protocol
  shape (`resolve.ts` + `lfs.ts` + `blobs.ts` standing in for the
  read-side trio that Maven splits as `read.ts` + `maven-metadata.ts`
  and NuGet splits as `service-index.ts` + `flat-container.ts` +
  `registration.ts`). A future maintainer can apply muscle memory
  from any other facade.
- **The `hf_revision` companion table is the first facade-introduced
  non-`manifest` table — document the rationale**:
  - The HF revision row's natural shape is `(org, repo, repo_type,
    revision) → files[]`. Storing this as a `kind:'hf'` manifest
    with empty `blobs: []` and the files-list inside an annotation
    or metadata field would work, but it would:
    - require shoehorning the composite key into `manifest.version`
      (the existing schema's only key), exactly the problem the
      composite key encoding (`<revision>:<percent-path>`) avoids
      for per-file rows;
    - mix two semantically distinct row types (per-file blob
      hydration anchors vs revision-tree manifests) into one table,
      and obscure the append-only constraint on revisions (which is
      stronger than the manifest table's "identical re-put OK" rule);
    - make the foreign-key relationship (`hf_revision` rows
      reference per-file `manifest` rows by sha256) implicit.
  - We chose a sibling table with its own composite PK + a foreign-
    key-ish JSON `files` column. This makes the boundary explicit:
    `manifest` holds blob hydration anchors keyed by content; `hf_revision`
    holds the tree manifests keyed by the operator-supplied revision
    name. Future v0.7 git-push will likely add `hf_branch` and
    `hf_tag` companion tables in the same shape.
  - The trade-off: code touching HF rows must consult both tables.
    We hide this behind the `resolveHfFile` + `publishHfTarball`
    APIs so callers (`mount.ts`, the integration tests, future
    operators) never see the dual-table layout directly.
- **Streaming end-to-end**: the publish path streams the USTAR
  body through a `BufferedReader` + `HashingPassthrough` into
  `storage.putBlob`; the resolve path's Range handler reads chunks
  off the source stream and forwards only the requested slice. No
  multi-GB buffer accumulates anywhere on either path. The hand-
  rolled tar parser is ~370 lines because the M4 conformance
  surface is `tar -cf model.tar .` + `--format=ustar`; GNU + PAX
  extensions are rejected up front rather than supported.
- **Manifest.version key encoding**: the registry's existing
  `validateManifestVersion` forbids `/`, so the HF per-file row's
  key is `<revision>:<percent-encoded-path>` (`/` and `%` escaped;
  everything else preserved). The encoder is local to
  `hf/paths.ts`; callers use `hfManifestVersion(revision, path)`
  + `parseHfManifestVersion(key)` and never see the encoding.
- **Routing**: greedy `/hf/:org/:repo/*rest` with internal dispatch
  on the path suffix (matches the Maven facade). The two anchor
  POSTs (`/upload-tarball`, `/info/lfs/objects/batch`) are explicit
  routes so the router's pattern matcher doesn't accidentally
  shadow them with the greedy GET.

### Lens 3 — Product

**PASS.**

- **`huggingface-cli download <org>/<repo>` flow works end-to-end**:
  the integration test publishes a tarball, then exercises both the
  raw-bytes path (small files) and the LFS-pointer path (large
  files). The pointer is the canonical 3-line text
  `huggingface-cli` expects, and the `lfs/sha256/<hex>` href the
  Batch endpoint emits is the URL the CLI's LFS resolver hits next.
- **Loom HF integration gating note** (per the WS13 prompt M4
  closure criterion): M4 is the milestone that unblocks Loom agent
  fine-tunes. The flow is:
  1. Operator publishes a fine-tuned model to the registry's HF
     facade via `huggingface-cli` or the `POST /upload-tarball`
     endpoint;
  2. Loom agent's `huggingface-cli download` (or `transformers`
     `from_pretrained(...)` against the registry-as-mirror) pulls
     the bytes;
  3. Audit-log + provenance row traces every byte back to either
     the local upload or the virtual upstream's `huggingface.co`
     mirror.
  The CLI smoke is *manual* at M4 close (the env-gated
  conformance lane); a real Loom integration in v0.7 will replace
  the manual smoke with an automated end-to-end test.
- **Cache miss propagation matches HF wire semantics**: 404 with
  `{"error": "Repository not found"}` for unknown repos; 404 with
  `{"error": "Revision not found"}` for known repos with unknown
  revisions; 404 with `{"error": "Entry not found"}` for known
  revisions with unknown file paths. `huggingface-cli` reads these
  and emits the friendly "Repository not found" message in its
  CLI output.
- **Bearer auth surface**: operators plumb their HF PAT into
  `virtual_upstream.config.auth_header_template: "Bearer hf_<token>"`.
  The token never appears in error messages (`redactBearerToken`)
  or audit logs (`redactDetail`). The HF UI's
  `~/.cache/huggingface/token` file is intentionally NOT read
  server-side — operators must configure the token explicitly,
  matching the upstream-auth pattern from the cargo / npm / Maven
  facades.
- **Manual smoke instructions** (not run in this commit; documented
  here for operator follow-up):

  export HF_HUB_TOKEN=sk_<ops>

### Lens 4 — Security

**PASS.**

- **Bearer token redaction**: `redactBearerToken` in `hf/errors.ts`
  catches `Bearer <token>` substrings in error messages and the
  generic envelope. `redactDetail` recursively walks the audit
  `detail` object; any key matching `Authorization` (case-
  insensitive) or `auth_header_template` collapses to `<redacted>`.
  Tested: `hf-errors.test.ts` `redactDetail walks string fields +
  arrays` + `redacts Authorization-key + auth_header_template`;
  `hf-virtual.test.ts` `forwards Bearer auth to upstream + redacts
  in the audit log` end-to-end check via JSON.stringify on the
  audit row.
- **Symlink + path-traversal rejection on tar entries**: `parseUstarTar`
  rejects typeflags 1/2/3/4/6 (hardlink/symlink/chardev/blockdev/FIFO),
  L/K (GNU long-name/long-link), x/g (PAX), and any unknown typeflag.
  `validateHfPath` rejects empty / absolute / trailing-slash / NUL /
  control / backslash / `..` paths. Tested: `hf-publish.test.ts`
  `rejects symlinks`, `rejects path traversal in entries`,
  `rejects hardlinks`, `rejects device files / FIFOs`,
  `rejects GNU long-name / PAX headers`.
- **50 GB blob cap honoured + override knob**: `enforceMaxBlobBytes`
  trips TOO_LARGE (413) when a tar entry's declared size exceeds
  the cap. Operator override via `virtual_upstream.config.hf_max_blob_bytes`
  takes priority on per-upstream publishes; the default is the
  50 GB lock from Q1.
- **XML hardening inherited via the PypiError pattern**: HF M4
  doesn't parse XML directly (the HF protocol is JSON-only —
  Batch + tree responses + error bodies are all JSON). The PyPI
  facade's defensive XML parser (DOCTYPE/CDATA/depth-cap rejection)
  is the security-pattern reference for any future HF dataset-
  card-XML extension.
- **Range request bounds checking**: `parseRangeHeader` rejects
  multi-range, suffix-of-0, start >= total, end < start, non-
  integer, and non-`bytes=` units. The blob streamer clamps end
  to `total - 1` when the client requested beyond the blob. Tested
  in `hf-guards.test.ts` for every documented form + `hf-resolve.test.ts`
  end-to-end.
- **LFS bytes sha-verify**: `proxyHfLfsBatch.fetchLfsBytes` re-
  hashes the bytes the upstream returns and rejects with
  `lfs_blob_sha_mismatch` if they don't match the declared OID.
  This is the explicit defence against an upstream LFS provider
  serving bytes that don't match the declared OID — could be a
  drift / cache-corruption + an active substitution attack.
- **Audit-log `proxy_cache` action with HF phases**:
  `metadata` / `resolve` / `lfs_batch` / `blob_bytes` + their
  `_error` siblings, mirroring the cargo / npm / Maven phasing.
  Bearer tokens are stripped before serialisation; every audit
  row carries `upstream_url`, `upstream_id`, `org`, `repo`,
  `repo_type` plus phase-specific fields.

## Format-spec source

Manifest schema + path conventions cited from the Claude Code plugin
reference at <https://code.claude.com/docs/en/plugins-reference>,
fetched 2026-05-17 by the agent. Permissions schema cited from
<https://code.claude.com/docs/en/permissions>, same date.

Confirmed facts that drove design choices:
- Manifest path is `.claude-plugin/plugin.json` (not bare
  `plugin.json` as the design doc hedged).
- Only `name` is required; all other fields are optional metadata.
- `skills/` is auto-discovered with no manifest entry needed.
- `commands/<name>.md` is the slash-command file format.
- `mcpServers` is an inline object map; key is the server's
  identifier used in `mcp__<server>__<tool>` permission patterns.
- Plugin-scoped `settings.json` accepts ONLY `agent` and
  `subagentStatusLine` — there is no plugin-shipped permissions
  block, so the preset must ship as documentation.

## Spec drifts vs design doc

Three drifts were reconciled in-flight:

1. **MCP invocation form.** Design doc Story 1 suggested
   `signalman serve --mcp` based on the operational prompt. The
   host's actual MCP entrypoint per `host/src/server.ts` ll. 19–22
   is `node host/dist/server.js` (stdio MCP server, not the HTTP
   control plane `signalman serve` produces). The manifest uses
   `node ${CLAUDE_PROJECT_DIR}/host/dist/server.js`.
2. **Skill location (Q3 lock vs marketplace caching).** Design doc
   Q3 lock says "skills at repo-root, plugin references them". The
   spec says installed plugins cannot reference files outside their
   directory, and symlinks pointing outside the plugin are stripped
   at marketplace install. Reconciliation: ship symlinks in
   `plugin/skills/<name>` pointing back to `../../skills/<name>`.
   Works for the `--plugin-dir` local-dev install path (the v0.1.0
   acceptance audience). Marketplace publish requires either a
   build-step copy OR a Q3 re-litigation. Documented in
   `plugin/TESTING.md` §"Known limitations" + `plugin/README.md`
   §Locked decisions Q3. The operator decides at marketplace time.
3. **Permission preset shape.** Design doc Story 4 implied the
   preset lives in the manifest. The spec confirms it cannot; ships
   as `PERMISSIONS.md` + `settings.json.example` instead.

Per the operator's standing workstream convention (CLAUDE.md +
`docs/design/v0.5-claude-plugin.md` §Coverage gate).

### QA lens — PASS

- 58 manifest-validation asserts pass, including the drift-detection
  asserts that cross-check the preset against the live host tool
  registry.
- The slash-command markdown body is asserted to mention all 5
  required MCP sub-queries; an accidental drop of any sub-query
  fails the test.
- The 6 skills are asserted to (a) be the exact set declared,
  (b) resolve to a real SKILL.md via the plugin tree, (c) resolve to
  a real SKILL.md via the canonical repo-root tree.
- README is asserted to mention all 5 locked decisions Q1–Q5 plus
  uninstall, version compat, 6 skills by name, the slash command,
  MCP, ROADMAP cross-ref.
- One known-fail in host's pre-existing `cli-version.test.ts`
  (environmental, not WS7-caused, see above).

### Architecture lens — PASS

- Manifest filename + path verified against the official format spec
  (fetched 2026-05-17). No invented fields.
- MCP server invocation points at the host's real stdio MCP entry
  (`host/src/server.ts` ll. 19–22 documents this exact invocation as
  the supported install form).
- Plugin-internal symlinks resolve within the plugin root and do not
  introduce out-of-tree dependencies that would break marketplace
  install — except the skill symlinks, which are a known design-doc
  / spec drift documented above. Workstream-bounded resolution
  (build-step copy at marketplace publish) is sufficient for v0.1.0
  scope.
- No new third-party dependencies. The test file uses only
  `vitest` (already in host workspace) and node built-ins (`fs`,
  `path`, `url`). `selvedge.check_package` not needed.
- Plugin packaging is fully decoupled from host source: no edits in
  host/guest/service/registry/loom-plugin source per DoD §8.

### Product lens — PASS

- All 5 locked decisions Q1–Q5 are recorded in `plugin/README.md` and
  cross-validated by tests. Operator-authorised 2026-05-17; no
  re-litigation.
- Day-2 SRE flavoring (Q2) is enforced via the slash-command body
  ("broken / pending / stale" framing) and a regression-guard test.
- The 6 chosen skills match the design doc + ROADMAP (day-1 happy
  path + day-2 essentials + Wave-B showcase + forensic + target
  setup).
- Out-of-scope items deferred to v0.2.0 are documented in
  `plugin/README.md` §"What's deferred" — operator + contributor
  expectations are calibrated.
- Permission preset categorisation reflects the operator's stated
  intent (`plugin/ROADMAP.md` v0.1.0): read-only → allow, recoverable
  state-change → ask, destructive/root-of-trust → deny.

### Security lens — PASS with one concern

- Destructive-verb deny list covers: key generation, signing-key
  rotate/revoke/add (cryptographic root of trust); credential
  remove; cloud terminate + stack destroy (infrastructure tear-down);
  *_remove and runner_deregister (tombstoning).
- The "allow" tier excludes any tool that could exfiltrate secrets:
  `signalman_creds_get` is included but the host redacts sensitive
  fields server-side (verified against
  `host/src/verbs/cloud.ts:redactCloudCredentialFields`).
- The slash command playbook explicitly says NOT to call
  `signalman_status` (which has different semantics — scenario-run
  status, not deployment status) so an over-eager Claude doesn't
  produce misleading output that an operator might act on.
- Permission preset shipped as documentation, not enforced by the
  plugin. **Concern:** if an operator forgets to apply the preset,
  Claude Code default-prompts behaviour governs. Mitigation: the
  README and TESTING.md both lead with the manual preset-application
  step. A v0.2.0 follow-up could ship a PreToolUse hook bundled with
  the plugin to enforce the deny tier even without user settings.
- No telemetry, no network beacons, no opt-in usage analytics in
  v0.1.0 (Q4 lock). Plugin is silent.
- Manifest does not declare any `userConfig` requiring sensitive
  values (no plugin-side credential prompting).
- All third-party dependencies in the plugin tree are inherited from
  the host workspace's `node_modules` via symlink — no new deps
  introduced.

**Concern raised:** preset is advisory, not enforced. Operator-side
mitigation documented. v0.2.0 follow-up (PreToolUse hook for the deny
tier) noted in PERMISSIONS.md §"Future work".

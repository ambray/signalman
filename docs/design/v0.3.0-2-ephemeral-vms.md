# v0.3.0-2 — Ephemeral VM Provisioning (design note)

**Status**: in progress on `feat/v0.3.0-ephemeral-vms` branch (worktree at
`../signalman-v030-ephemeral-vms`).

**Companion design**: `docs/design/meta-build-system.md` §13 (cloud) feeds
on the `vm_lineage_hash` and provisioning patterns landed here.

---

## 1. Problem

Today, scenarios assume a VM named `vms[].name` already exists on the
host (`DESKTOP-FAF4PL7`-pinned for development, hand-named checkpoint).
This blocks:

- True repeatability — multi-scenario runs leak state into each other
  because they all reuse the same long-lived VM.
- Repeatability across hosts — moving CI to a new host requires
  manually rebuilding the same VM topology.
- `vm_lineage_hash` (v0.3.0-3 envelope work) — there is no concept of
  a base image + change-set to hash today; the VM identity *is* its
  hand-built state.
- Cloud-provider work (v0.3.0-5) — the same provisioning patterns
  (`vm_lineage_hash`, ephemeral lifecycle, golden-image manifests)
  need to compose for AWS / Azure backends.

## 2. What already exists (do not rebuild)

- `host/src/scenarios/templates.ts` — `VmTemplate` interface,
  `resolveTemplateAsync()` that materialises a base VHDX on disk from
  either a BYO path or a verified HTTPS download. P9.5 / v0.1.1.
- `host/src/provisioning/template-fetch.ts` — HTTPS-only, SHA-256-
  verified, atomic-rename download pipeline.
- `host/src/hypervisors/hyperv.ts` — `HyperVBackend` with `createVM`,
  `deleteVM`, `copyFileToVM`, checkpoint operations.
- `service/proto/signalman_service.proto` — already declares
  `rpc VmCopyFile(VmCopyFileRequest) returns (stream VmCopyFileEvent);`.
  The streaming side is wire-ready; the host client just doesn't
  consume the stream events yet.

## 3. What ships in this epic

### 3.1 Differencing-disk pipeline (`host/src/provisioning/differencing-disk.ts`)

A pure module that wraps Hyper-V's `New-VHD -ParentPath <parent>
-Path <child> -Differencing`. Inputs:

```ts
interface CreateDifferencingDiskOptions {
  parentVhdxPath: string;     // absolute, must exist
  childVhdxPath: string;      // absolute, must not exist
  // Injectable PS exec for tests.
  exec?: (script: string, timeoutMs?: number) => Promise<string>;
}
```

Locked rules:

- Parent path must exist on disk. Validated before invoking PS.
- Child path must NOT exist. We never silently overwrite.
- Parent and child must be on the same volume (Hyper-V requirement
  for differencing chains on Server 2016+; checked via
  `path.parse(...).root` comparison before invoking PS).
- Generates a structured error when `New-VHD` fails — not a raw PS
  stack trace.

This module is pure: no orchestrator dependency, no file-system
ambient state beyond the explicit paths. Tested in isolation.

### 3.2 Ephemeral VM lifecycle (orchestrator wiring)

In `host/src/scenarios/orchestrator.ts` `resolveVms()`:

For each `VmConfig` in the scenario:

- **Branch A — `vm.template` is set** (new, v0.3.0):
  1. `await resolveTemplateAsync(vm.template)` → base `vhdxPath`.
  2. Generate ephemeral name:
     `<scenario-slug>-<vm.name>-<runId.slice(0, 8)>`. Sanitised for
     Hyper-V (no `:`, `\`, `/`; max 64 chars).
  3. Compute child VHDX path:
     `<workspaceRoot>/.signalman/ephemeral-disks/<ephemeral-name>.vhdx`.
  4. `await createDifferencingDisk({ parentVhdxPath: base, childVhdxPath })`.
  5. `await backend.createVM({ name, vhdxPath: childVhdxPath, ... })`.
  6. Record the ephemeral VM + child VHDX in the scenario's resource
     ledger so teardown removes them.

- **Branch B — `vm.template` is not set** (legacy):
  1. Look up VM by name on the backend. If found, use it. If not
     found and `vm.provision_if_missing` is truthy, fall through to
     branch A using a default template. Otherwise, error.

Teardown order: `vm.stop()` → `vm.delete()` → `fs.rm(childVhdxPath)`.

**Cleanup reaper integration**: the existing scenario-orphan-cleanup
reaper (per docs/STATUS.md) gets a new pass for stale entries in
`.signalman/ephemeral-disks/` whose corresponding VM no longer
exists. Out of scope for the initial commit; tracked as follow-up.

### 3.3 `vm_lineage_hash` (envelope contribution)

Computed by the orchestrator at provision time:

```json
{
  "template_name": "win11-base",
  "template_version": "<from template manifest, if present>",
  "os": "windows-11",
  "installed": [
    {"name": "<bundle name>", "version": "<bundle version>"}
  ]
}
```

Sorted keys, sorted `installed[]` by `name`, canonical JSON, SHA-256.
The hash is recorded against the ephemeral VM in the result envelope.

This is technically a v0.3.0-3 deliverable (Hermetic Envelope), but
the hash is *computed* during -2 because the inputs are only
available at provision time. The envelope-graduation work in -3 will
expose the field through the public envelope shape; -2 just stores
it on the internal scenario-run record.

### 3.4 Streamed `vm_copy_file` progress (C8)

Two paths to fix:

**(a) Direct-PowerShell `HyperVBackend.copyFileToVM`**:
- The `_progress` callback is accepted but unused.
- For files > 100 MB: wrap the `Copy-VMFile` PowerShell invocation in
  a polling loop. While the PS job runs, sample the destination file
  size every 2 seconds and emit a `{ bytesCopied, totalBytes }`
  event to `progress`. Closes the "multi-GB copy appears hung" UX
  issue.
- For files ≤ 100 MB: skip the polling overhead; emit a single
  start + complete event.

**(b) Service-backed copy**:
- The service-side proto already declares the streaming RPC. The
  host's `service-backend.ts` (TypeScript service client) currently
  consumes the unary form. Update the client to consume the stream
  and forward events to `progress`.

### 3.5 `template:` field wiring (C9)

Previously `template:` was decorative. Now it drives branch A above.
Documentation update: README's scenario-format section needs a
`template:` example and a note that it's the recommended path going
forward.

## 6. Risks

- **Differencing-chain depth** — Hyper-V supports up to 13 levels in
  a differencing chain. Per-scenario ephemeral disks are depth-1
  (parent = base, child = ephemeral). No nesting.
- **Same-volume requirement** — operators may have base images on D:
  and want ephemeral disks on a faster scratch volume. v0.3.0-2 forces
  same-volume; cross-volume requires copying the parent first, which
  defeats the differencing-disk point. Documented as a constraint.
- **Concurrent scenario runs** — two scenarios on the same template
  create two different ephemeral disks under different names. No
  collision. The base VHDX is read-only at the OS level for any
  child; multi-reader is safe.

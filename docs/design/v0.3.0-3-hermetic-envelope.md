# v0.3.0-3 — Hermetic Envelope (design note)

**Status**: in progress on `feat/v0.3.0-hermetic-envelope` branch
(worktree at `../signalman-v030-hermetic-envelope`), branched off
v0.3.0-2 since this work depends on `vm_lineage_hash` landing first.

---

## 1. Problem

Today's `ScenarioResult` envelope carries `name`, `status`,
`duration_ms`, setup/assertion/teardown results, and optional error.
It does NOT identify:

- **What scenario actually ran** (no hash of the scenario YAML
  content). Two scenarios named `"smoke"` in different repos
  produce indistinguishable envelopes; a scenario that's been edited
  between runs is also indistinguishable from its previous version.
- **What VM it ran on** — beyond the logical name. The
  `vm_lineage_hash` computed in v0.3.0-2 stays internal to the
  orchestrator's resource ledger.
- **What guest-agent version executed it.** A scenario passing on
  agent 0.1.x but failing on 0.2.0 surfaces as "the scenario broke"
  rather than "the agent's contract changed".
- **What network class the run used.** Internet-reachable runs vs
  isolated-lab runs are operationally meaningful but indistinguishable
  in current output.

Downstream consumers (Loom workflow caching, audit trails, CI
result dashboards) can't safely short-circuit identical inputs
without these. v0.3.0-3 closes the gap.

## 2. What ships in this epic

### 2.1 `scenario_hash` — content-addressed scenario identity

A pure helper that hashes the three scenario artifacts:

```
scenario_hash = sha256(canonical-json({
  setup:      sha256(canonical-json(parsedSetupYaml)),
  assertions: sha256(canonical-json(parsedAssertionsYaml)),
  workflow:   sha256(normalize-lf(workflowMarkdown))
}))
```

Locked decisions:

- **Hash the parsed form, not raw bytes.** Comments and whitespace
  in the YAML don't change the hash. Caught accidental no-ops
  (file touched without semantic change) becoming false cache misses.
- **Hash the unresolved form.** `${param:NAME}` references stay
  literal in the hash. The cache layer (v0.3.0-3 follow-up) keys on
  `(scenario_hash, params_hash, vm_lineage_hash, agent_version)`
  so parameterised runs cache separately per parameter set.
- **LF-normalised workflow content.** CRLF vs LF doesn't change the
  hash; BOM is stripped. Editor-write differences don't invalidate
  caches.
- **Order-independent**: canonical JSON sorts object keys at every
  level (same pattern as `vm_lineage_hash` in v0.3.0-2).

### 2.2 `network_class` — operator-visible network identity

A pure helper that classifies a VM's network configuration into a
single stable string. v0.3.0-3 ships a thin pass-through; richer
classification (NAT detection, internet-reachability probes) is
reserved for v0.4.0+.

Rules:

- `pre_started: true` → `"pre-started"` (operator owns the network)
- `network.switch` declared → sanitised switch name (e.g.
  `"default-switch"`, `"isolated-lab-switch"`)
- Nothing declared → `"default"`

Operators encode the meaningful classes in their switch names; the
helper just normalises them.

### 2.3 `agent_version` — guest-agent version capture

The guest agent's `Health` RPC already returns `agentVersion`. The
orchestrator calls health probes during `waitForGuestAgents`; we
capture the version on the way through and store it on the result.

Multi-VM scenarios get the sorted+deduped set of versions, joined
with `,`. Single-version cases stay as a plain version string.
Scenarios where no agent ever reported (failure mode) get
`undefined`.

### 2.4 Envelope graduation

Extend `ScenarioResult` (host/src/scenarios/orchestrator.ts) with
four new optional fields:

```ts
interface ScenarioResult {
  // ...existing fields
  scenario_hash?: string;     // 64-char hex
  vm_lineage_hash?: string;   // 64-char hex; derived from ephemeral VM
  agent_version?: string;     // comma-joined version set
  network_class?: string;     // operator-derived class label
}
```

Optional initially so existing consumers (JUnit report writer,
audit log) don't break. The orchestrator always populates them when
it has the data.

For multi-VM scenarios, `vm_lineage_hash` is the SHA-256 of the
canonical JSON of an array of per-VM lineage hashes (sorted). This
gives the multi-VM case a stable single-string identity without
losing per-VM detail.

## 3. Out of scope (deferred)

- **Cache layer**: the envelope graduation makes caching possible
  but doesn't implement the cache itself. A v0.3.0-3 follow-up
  ships `cache_lookup(scenario_hash, params_hash, vm_lineage_hash,
  agent_version) → ScenarioResult | null` and the `cache_put` after
  a passing run. Out of scope here because it touches the storage
  layer and adds new control-plane surface.
- **Network-class richness**: NAT detection, internet-reachability
  probes, IP-range classification. v0.4.0+ once a real consumer
  asks for it.

## 4. Sub-task sequence

1. **`scenario_hash` + `network_class` helpers + tests** (this
   commit) — pure modules. No orchestrator changes.
2. **Envelope graduation + orchestrator wiring** — extends
   `ScenarioResult`, captures the hashes during `runScenario`.
3. **Multi-VM `vm_lineage_hash` aggregation** — when there's more
   than one ephemeral VM, combine their per-VM hashes into a single
   envelope-level hash.
4. **Cache layer** (follow-up epic, NOT v0.3.0-3) — keyed on the
   full triple + params hash.

# v0.3.0-4 — Loom Orchestrator Contract (design note)

**Status**: in progress on `feat/v0.3.0-loom-contract` branch
(worktree at `../signalman-v030-loom-contract`), branched off v0.3.0-3
since this work consumes the envelope graduation.

---

## 1. Problem

v0.3.0-3 graduated `ScenarioResult` with the hermetic identity
fields (`scenario_hash`, `vm_lineage_hash`, `agent_version`,
`network_class`). The Loom plugin already passes the envelope
through unchanged via `loom.signalman.status`, so Loom workflows
CAN read those fields — but only by descending into
`response.envelope.scenario_hash`. That's awkward for cache-keying
and means workflow nodes have to handle the "envelope shape is
optional" branch carefully.

v0.3.0-4 closes this by promoting the identity fields to first-class
task evidence on the plugin's response shape: workflow nodes read
`response.hermetic_identity.scenario_hash` directly without
parsing envelope JSON, and Loom's caching layer keys on a stable
top-level object.

## 2. What ships in this epic

### 2.1 `hermetic_identity` response object

A new top-level field on `loom.signalman.run` (when envelope is
immediate-terminal) and `loom.signalman.status` (when the run has
reached a terminal state) responses:

```json
{
  "run_id": "abc...",
  "status": "passed",
  "envelope": { /* full ScenarioResult */ },
  "hermetic_identity": {
    "scenario_hash": "0a1b2c...",
    "vm_lineage_hash": "f4e5d6...",
    "agent_version": "0.2.1",
    "network_class": "default-switch"
  }
}
```

Rules:

- Populated only when the envelope is present AND at least one
  identity field is non-empty. Workflows that gate on
  `hermetic_identity` know an envelope already exists.
- Mirrors the envelope's identity subset exactly — no derivation,
  no field renames. Promotion is structural only.
- Backward-compatible: the existing `envelope.scenario_hash` path
  continues to work; `hermetic_identity` is additive.

### 2.2 Direct CLI/CI orchestration path documented

For consumers who don't want Loom in the loop (raw GitHub Actions,
third-party CI, ad-hoc operator runs), the CLI exit codes +
envelope JSON on stdout remain the contract. README adds a
"Orchestration paths" subsection making both paths explicit:

- **Loom-fronted (default)**: agent → MCP `loom.signalman.run` →
  plugin → `signalman` subprocess. Loom owns run state, event
  streaming, retry, and task evidence.
- **Direct CLI/CI (advanced)**: caller → `signalman run <scenario>`
  → envelope JSON on stdout. Caller owns scheduling + retry.

### 2.3 Naming clash deferred (documented)

`network_class` exists in two places:

- **Input** to `loom.signalman.run` — `enum [isolated, nat, internet]`
  declaring the intended isolation. Reserved for P4 enforcement;
  currently advisory.
- **Output** on `ScenarioResult` envelope (v0.3.0-3) — sanitised
  switch name describing the network the VM actually ran on
  (`"default-switch"`, `"pre-started"`, etc.).

These have different shapes and meanings. v0.3.0-4 documents the
distinction; a rename of the input to `requested_network_class`
is tracked as a v0.3.0-4 follow-up so this epic stays scoped to the
envelope-promotion + docs work.

## 3. Out of scope (deferred)

- **Loom workflow node template**: a YAML/Rust template showing
  exactly how a Loom workflow would compose `loom.signalman.run`
  with cache lookup keyed on `hermetic_identity`. The plugin
  exposes the primitive; the template is Loom's concern.
- **Plugin-side cache implementation**: same as v0.3.0-3 — the
  envelope graduation makes caching possible, but the cache layer
  itself ships as a separate follow-up.

## 4. Sub-task sequence

1. **`extract_hermetic_identity` helper + tests** (this commit) —

2. **Schema updates + handler wiring** — promote the field through
   status + run responses.
3. **README orchestration-paths docs**.
4. **(follow-up) Input rename** — `network_class` → `requested_network_class`.

# v0.3.0-5 — Cloud Provider Support (design note)

**Status**: in progress on `feat/v0.3.0-cloud-providers` branch
(worktree at `../signalman-v030-cloud`), branched off main after the
v0.3.0 follow-ups consolidated.

**Companion**: `docs/design/meta-build-system.md` §13 — the
full-system design that this epic implements.

---

## 1. Problem

v0.3.0-2 through v0.3.0-1 wired record/replay + ephemeral VMs
against Hyper-V on Windows. That's a great fit for in-house CI on a
dedicated host, but signalman's reach is limited to whatever the
operator can stand up locally. The biggest constraints:

- **No cloud VMs for test fixtures.** Scenarios needing fresh
  ubuntu-22.04 + a public IP today require an operator to
  manually create the VM in AWS/Azure and reference it.
- **No multi-resource cloud stacks for deploy targets.** A
  scenario targeting a 3-tier deployment (VPC + ALB + RDS + EC2)
  has no way to declare that stack in the YAML.
- **No Kubernetes targets.** Manifests-based deploy + Job-based
  runner substrate are both useful primitives missing today.

v0.3.0-5 closes these by adding cloud-aware target kinds:
`cloud_vm_test`, `cloud_stack_test`, `k8s_test`. Each routes through
a new `CloudBackend` interface that parallels the existing
`HypervisorBackend`.

## 2. Workload split (locked, per meta-build §13)

Two distinct driver paths, chosen by the cost / control trade-off
of each workload:

- **Direct vendor SDK** (boto3-equivalent for AWS, Azure SDK for
  JS for Azure):
  - **Ephemeral test VMs** (`cloud_vm_test`) — provision EC2 / Azure
    VM, wait for IP, run scenario, terminate. Wall-clock-TTL'd and
    budget-gated.
  - **Cloud runners** — same shape; the runner stays up for the
    scenario duration.
- **OpenTofu (subprocess)**:
  - **Deploy targets** (`cloud_stack_test`) — operator-authored or
    starter-library HCL applied via `tofu apply`; `tofu destroy`
    on teardown.
  - **Kubernetes deploys** (`k8s_test`) — manifests-first; HCL is
    used only to provision the cluster itself (out-of-scope until
    v0.3.0-6).

License decision: OpenTofu is MPL-2.0, subprocess-safe for both
the Apache-2.0 OSS distribution and the proprietary commercial
fork. Confirmed in v0.3.0 design session.

## 4. What ships in THIS commit (sub-task 1)

### 4.1 New namespace `host/src/cloud/`

Mirrors the existing `host/src/hypervisors/` shape:

```
host/src/cloud/
├── types.ts        — CloudBackend interface, CloudInstanceConfig,
│                     CloudInstanceHandle, CloudInstanceStatus,
│                     CloudBackendKind, CloudTargetKind, errors
├── registry.ts     — register/look up backends by kind
└── (future)        — aws.ts, azure.ts, tofu.ts, k8s.ts
```

### 4.2 `CloudBackend` interface

Methods:

- `name: CloudBackendKind` — `"aws" | "azure" | "gcp" | "ibm"` etc.
- `provisionInstance(config: CloudInstanceConfig): Promise<CloudInstanceHandle>`
- `terminateInstance(handle: CloudInstanceHandle): Promise<void>`
- `getInstanceStatus(handle: CloudInstanceHandle): Promise<CloudInstanceStatus>`
- `getInstanceIp(handle: CloudInstanceHandle): Promise<string | null>`
- `listInstances(filter?: { tags?: Record<string, string> }): Promise<CloudInstanceHandle[]>`

Locked decisions:

- **No checkpoint/snapshot methods.** Cloud VMs don't have the
  Hyper-V "checkpoint then restore" lifecycle. If a scenario
  needs to repeatedly reset a VM's state, it provisions a new
  ephemeral instance per run (the existing v0.3.0-2 pattern, but
  with cloud as the substrate).
- **`provisionInstance` is async.** Production calls wait for the
  cloud to confirm the instance is `running`, then return the
  handle. Tests inject a stub that returns immediately.
- **TTL is encoded in the config, not enforced by the backend.**
  Sub-task 6 (cost guardrails) ships a reaper that polls
  `listInstances` filtered by Signalman tags and terminates past
  TTL. The backend itself stays simple.
- **`listInstances` filters by tag.** Every Signalman-provisioned
  cloud instance is tagged `signalman-managed=true` +
  `signalman-org=<org_id>` so the reaper can identify them
  without leaking other workloads.

### 4.3 `CloudTargetKind` enum

Three new target kinds extending the scenario YAML:

```yaml
vms:
  - name: ephemeral-vm-1
    target_kind: cloud_vm_test     # new in v0.3.0-5
    cloud:
      provider: aws
      region: us-east-1
      instance_type: t3.medium
      image_id: ami-0abcd...      # pre-baked golden image
      ttl_minutes: 60
```

Or for stack tests:

```yaml
stacks:                            # new top-level key (sub-task 4)
  - name: backend-three-tier
    target_kind: cloud_stack_test
    cloud:
      provider: aws
      tofu_module: aws-three-tier
      vars:
        instance_count: 2
        region: us-east-1
      ttl_minutes: 120
```

This commit declares the enum + types. Scenario-schema wiring
lands with sub-task 2 (when the first concrete provider arrives).

### 4.4 Errors

`CloudBackendError` with stable `code`:

- `unsupported_provider` — registry lookup failed
- `provision_failed` — backend rejected the provision call
- `terminate_failed` — backend rejected the terminate call
- `instance_not_found` — handle stale
- `ttl_expired` — guard surfaces this when reaper terminates
- `auth_failed` — credential resolution / API auth failure
- `quota_exceeded` — cloud quota / budget refused the call

### 4.5 Registry

```ts
registerCloudBackend(kind: CloudBackendKind, factory: () => CloudBackend);
getCloudBackend(kind: CloudBackendKind): CloudBackend;
listRegisteredBackends(): CloudBackendKind[];
```

Module-singleton registry; backends register themselves at module
load time (like `inventory::submit!` in Rust). Tests reset the
registry between cases.

## Coverage gate (operator-mandated for this round)

The original prompt says "Test taxonomy is light — Unit: none
required, Integration: none required". The operator amended this
2026-05-17 to the standing project convention:

> **Every story validates ≥80% test coverage** (lines AND
> branches) on any new TypeScript code added in that story.

For WS7 specifically:

- **Stories that add manifest / markdown only** (e.g. skill
  index, README, slash-command markdown) are exempt from the
  80% gate but must ship a manifest-validation test that loads
  the manifest, asserts the schema is well-formed (required
  fields, no unknown fields, paths resolve to actual files),
  and asserts the declared skills/commands point at existing
  files on disk.
- **Stories that add TS code** (e.g. a JS-side validator,
  permission-preset enforcer, slash-command implementation if
  it grows beyond markdown) hit the standard 80/80 gate per
  file.

For the v0.1.0 MVP scope (manifest + 6 skill refs + one slash
command + permission preset + README), most of the code is
manifest/markdown. The manifest-validation test (story 6
below) is the load-bearing coverage gate.

## Stories

The original prompt lists 5 milestones; this design re-presents
them as 6 stories to thread the manifest-validation test into
its own story for clean coverage attribution. Order + commit
patterns match the prompt.

### Story 1 — Plugin scaffold + MCP registration (smallest, ship first)

- Create `plugin/` directory with:
  - Manifest (`plugin/plugin.json`. **Format-spec note:** the
    agent must do a focused web check (or `claude-code-guide`
    subagent) to confirm the current manifest filename and
    schema. If the spec dictates `manifest.json`, rename;
    don't invent fields.
  - `plugin/README.md` — install, uninstall, what's inside,
    version compat note.
  - `plugin/LICENSE` — Apache-2.0 symlink or copy.
- Manifest declares:
  - Plugin name: `signalman`
  - Version: `0.1.0`
  - MCP server registration pointing at `signalman serve --mcp`
    (confirm against `host/src/cli.ts` for the exact verb).
  - Empty skills, slash-commands, hooks arrays.
- **Manifest-validation test stub.** A trivial test that
  `JSON.parse`s the manifest, asserts required top-level fields
  exist, and asserts the MCP server invocation string is
  non-empty. Real schema validation lands in story 6.
- Manual install verification (subagent's own machine):
  `claude plugin install ./plugin` if available; otherwise
  document the steps in `plugin/TESTING.md` for the operator.

**Commit:** `feat(plugin): v0.1.0 scaffold + MCP registration`

### Story 2 — Skill index for the MVP 6

Wire these six existing skills into the manifest (paths
relative to repo root per Q3 lock):

- `signalman-build-from-tag`
- `signalman-deploy-to-test`
- `signalman-rollback`
- `signalman-promote-release`
- `signalman-query-audit-log`
- `signalman-register-target`

The skills directory is at `skills/<name>/SKILL.md`. The
manifest's skills array entries: `{name, path: "skills/<name>"}`.

**Test addition:** the manifest-validation test (story 6's
home) gets six asserts — for each declared skill, the
referenced `SKILL.md` exists on disk.

**Commit:** `feat(plugin): register the MVP 6 skills`

### Story 3 — `/signalman-status` slash command (the demo)

- New file: `plugin/commands/signalman-status.md` (or the path
  the format spec dictates).
- The slash command's "implementation" is a Markdown playbook
  Claude follows: chain a small number of MCP calls behind one
  entry point. Per Q2 lock, the answer leads with
  what's-broken/pending/stale.
- Synthesised answer covers:
  - Recent releases (last 5, with status: built / signed /
    deployed / failed).
  - Pending promotions (any `approval.status='pending'` with
    their age).
  - Failing probes (any `health_check.status='fail'` in the
    last hour).
  - Stale runners (no heartbeat in > 5 minutes).
  - Cloud budget status (only if cloud is configured;
    suppress otherwise).
- Acceptance: against a freshly-bootstrapped signalman with one
  product + one release, the command returns a coherent
  10-line answer in < 5 seconds.

**Test addition:** manifest-validation test asserts the
slash-command file exists at the declared path.

**Commit:** `feat(plugin): /signalman-status slash command`

### Story 4 — Permission preset

Per `plugin/ROADMAP.md`:

- **auto-allow:** `list`, `get`, `status`, `audit query`,
  `forensic`
- **prompt:** `build`, `deploy`, `promote approve`, `rollback`,
  `cloud-creds set`
- **deny:** `key generate`, `rotate-certs`, `cloud-creds remove`

The preset lives in the manifest (`permissions` block per
spec) or as a separate file referenced from the manifest.

**Verification:** trying one verb from each category produces
the expected behaviour. Document in `plugin/TESTING.md`.

**Test addition:** manifest-validation test asserts each
permission entry matches a real verb pattern (cross-checked
against `host/src/cli.ts` verb registry — load the verb list
at test time, assert each permission category matches at
least one verb).

**Commit:** `feat(plugin): permission preset for read/write/destructive verbs`

**Commit:** `docs(plugin): install + uninstall + version-compat + locked decisions`

### Story 6 — Manifest-validation test + 4-lens audit

Coverage-bearing story. Lands the test that drove asserts in

- New file: `plugin/__tests__/manifest-validation.test.ts`
  (or wherever the registry's vitest config will pick it up

- New file: `.workstream-status-ws7-m1.md` — 4-lens audit

  this workstream's commits introduced.

**Commit:** `test(plugin): manifest validation; docs(plugin): 4-lens audit for MVP closure`

## Test plan

### Unit lane (per-story)

Manifest-validation test grows incrementally across stories
1–5; coalesces in story 6 as a single ≥80%-coverage test
suite.

### Integration lane

Per the operator's amendment: any TS code added (slash command
helpers, permission enforcer, etc.) hits the 80/80 gate.
Manifest + markdown stays in the validation-test domain.

### System lane (gated, manual)

The original "manual install + invoke loop on a real Claude
Code install" — document the exact steps in
`plugin/TESTING.md`. Gate on agent-environment capability:
if `claude plugin install` is not available in the agent's
shell, document the steps and flag the operator to verify
manually before merging.

### Coverage targets

- Per story containing TS code: ≥80% lines AND ≥80% branches
  on each new TS file.
- Manifest + markdown stories: manifest-validation test asserts
  shape + cross-references; no separate coverage measurement.

### Lint + type gates

- `npx tsc --noEmit` from the relevant package directory clean.
- No new dependencies without `selvedge.check_package` (CLAUDE.md
  convention; agent should confirm Selvedge is installed; if
  not, surface the gap and proceed for now — pattern: a small
  hand-rolled schema check is fine).

## Definition of Done (must pass at story 6 completion)

1. `plugin/` directory with manifest, README, LICENSE, TESTING,
   slash-command file, manifest-validation test.
2. Manifest validation test passes locally (`npx vitest run
   plugin/__tests__/manifest-validation.test.ts`).
3. `/signalman-status` markdown body documents the synthesis
   logic; if any TS helper code is added, it's tested ≥80/80.
4. All 6 declared skills' SKILL.md files exist.
5. Permission preset matches the spec (verified by the
   validation test).
6. README documents install (marketplace + git-URL),
   uninstall, the 6 skills, the slash command, the 5 locked
   decisions, and the version-compat matrix.
7. 4-lens audit in `.workstream-status-ws7-m1.md` —
   QA / Architecture / Product / Security; each ends PASS or
   a specific concern.
8. No code in `host/`, `guest/`, `service/`, `registry/`,
   `plugins/signalman-loom-plugin/` source (this workstream is
   plugin-packaging only). If the agent finds itself wanting to
   change verb behaviour, it stops and surfaces to the operator.

## Problem statement

Today (2026-05-17) the only path from "empty Win11 VHDX" to
"VM running the Signalman guest agent" is hand-driven: the
operator opens an elevated PowerShell on the host, runs
`Set-VMFirmware -VMName <n> -EnableSecureBoot Off`, boots,
RDPs in, runs `bcdedit /set testsigning On`, reboots, drops the
test-signed `signalman-agent.msi` over a share, double-clicks it.
The Signalman provisioning pipeline (`host/src/provisioning/
provision.ts:1-29`) handles steps 5–7 of that flow (MSI discover
→ copy → install → checkpoint) but not steps 1–4.

`b0ec24c` and the earlier `vm install-bundle` work have closed
two of those four gaps:

| Gap | Closed by |
|---|---|
| `Set-VMFirmware -EnableSecureBoot Off` via CLI, not elevated PowerShell | `vm set-firmware <name> --secure-boot off` (`b0ec24c`) |
| Per-VM admin credentials in scenarios (Win11_test = test/test123, Win11_demo = demo/demo) | scenario-level `credentials:` + `withGuestCredentials` backend clone (`b0ec24c`) |
| `bcdedit /set testsigning On` from host, post-first-boot | **OPEN** — see Q1 |
| Test-signing-cert + MSI signing happens automatically as part of provision | **OPEN** — see Q2 + WS9 |

**This workstream closes the remaining two gaps** and binds the
existing six (template, create-VM, boot, certs, MSI install,
checkpoint) into one named verb (`signalman vm bootstrap-win11
<name> --template win11-base`) that an unprivileged operator can
run end-to-end. The output is a checkpoint named
`agent-installed` (or `--checkpoint LABEL`) on a Win11 VM with
the Signalman guest agent installed via a test-signed MSI, with
the same idempotency contract `provisionVM` already has (re-run
is a 2-second no-op when state matches).

The "Example tag-driven demo deploy pipeline" mentioned in
`b0ec24c`'s commit message refers to this verb. The eventual
goal is that a test owner tags a release `demo/<scenario>` and
the demo VM rebuilds itself from scratch.

## Goals

1. **Single-verb end-to-end.** `signalman vm bootstrap-win11
   <name> --template <win11-base|win11-dev|custom-yaml>` produces
   an `agent-installed`-checkpointed Win11 VM from nothing.
2. **Backend-agnostic where possible.** Hyper-V is the
   primary lane (the only backend that exposes `setVmFirmware`
   today). Libvirt support is goaled but separable — Q9 covers
   the staging.
3. **Idempotent + resumable.** Same contract as `provisionVM`:
   re-run is a no-op when checkpoint exists. Mid-pipeline
   failures leave the VM around for operator inspection unless
   `--cleanup-on-failure`.
4. **No elevated PowerShell on the host.** Every Set-VMFirmware
   / Hyper-V cmdlet is brokered through the service backend's
   mTLS gRPC. The operator running the verb does NOT need to be
   a member of `Hyper-V Administrators` interactively — the
   service runs as a controlled account.
5. **Coverage gate.** ≥80% lines / ≥75% branches on
   `host/src/provisioning/bootstrap-win11.ts` and any new
   files. Same gate that WS9 + libvirt-parity used.
6. **4-lens audit at each milestone close.** Per the repo
   convention.

## Non-goals

- **Windows Server.** This is Win11 specifically (workstation
   editions: Pro, Enterprise, Education). Server SKUs may
   eventually reuse parts, but the firmware/testsigning/MSI
   pipeline assumes workstation defaults.
- **Production WHQL-signed drivers.** The MSI we install in the
   demo is **test-signed**, not WHQL. The whole point of
   flipping Secure Boot off + testsigning on is so we can
   install drivers that no commercial signing authority would
   issue for. Customer-facing builds are a separate downstream.
- **Live customers / real telemetry.** This is an internal
   demo / smoke-test pipeline. It does not need to survive
   adversarial conditions.
- **macOS / Linux guests.** Linux + macOS scenarios go through
   `signalman vm provision` directly. They don't need the
   set-firmware step (no Secure Boot policy applies the same
   way) or the testsigning flag.
- **Live USB / external boot media.** The pipeline targets
   pre-staged Win11 templates (VHDX or qcow2). Building the
   golden image itself is out of scope — see "Golden image
   strategy" below.
- **In-place upgrades from Win10.** Templates are
   already-installed Win11. We don't drive setup.exe.
- **Customer-supplied trust roots.** The test-signing
   certificate this pipeline uses is operator-supplied via
   `--cert <path>` or env var. We do not run a CA.

## Locked design

Inferred from already-shipped scaffolding (`b0ec24c`, the
existing provision pipeline, WS9 signing, Win11 templates) +
operator commentary in `b0ec24c`'s commit body. Confirm with
operator at M0 gate; treat as proposed until then.

1. **Verb name: `signalman vm bootstrap-win11 <name>`.** Mirrors
   `vm provision` shape but with a Win11-locked template
   resolver. Both verbs co-exist; the new verb is just
   `provisionVM` + pre-steps (set-firmware) + post-steps
   (testsigning toggle, signed-MSI install).
2. **Templates remain in `.signalman/templates/win11-*.yaml`.**
   The two existing ones (`win11-base`, `win11-dev`) stay; the
   verb gains `--template <path-or-name>` resolver that's a
   thin wrapper over the existing `templates.ts`.
3. **Per-VM creds come from `setup.yaml`, not the verb CLI.**
   The bootstrap verb takes `--scenario <name>` (or the
   template carries `defaultCredentials:`) — credentials never
   appear on the CLI as plain text, mirroring the
   `${secret:NAME}` substitution path landed in `b0ec24c`.
4. **Set-firmware Off is the pipeline's first VM-modifying
   step.** Idempotent — calling it on a VM that already has
   Secure Boot Off is a no-op (`b0ec24c`'s Hyper-V impl emits
   `Set-VMFirmware -EnableSecureBoot Off` even when already
   off; Powershell doesn't complain).
5. **Testsigning toggle is driven from the host via
   `signalman vm exec <name> -- bcdedit /set testsigning On`.**
   Not a new verb. The bootstrap pipeline wraps `vm exec` +
   reboot. Pre-existing `--username/--password` overrides (or
   the new per-VM creds path) cover the elevation.
6. **MSI is signed by the operator's test-signing key chain
   before pipeline run, not inline.** The pipeline accepts a
   pre-signed MSI via `--msi <path>` or `--msi-from-build
   <buildId>`. Inline signing (calling WS9's signing service
   from the bootstrap) is deferred to v0.6.
7. **Reboot orchestration uses the existing scenario step
   primitives.** `vm reboot` + heartbeat wait + retry-on-time-
   out. No new RPC.
8. **Failure model: leave-the-VM (operator opt-in cleanup).**
   Same as `provisionVM`. `--cleanup-on-failure` opt-in.
9. **State persisted under `.signalman/state/bootstrap-win11/
   <vm-name>.json`.** Tracks which phases completed so a re-run
   resumes mid-pipeline rather than restarting from
   `set-firmware`. Same shape as the existing
   provisioning-state files.
10. **Hyper-V is M1; libvirt is M4.** See milestones — libvirt's
    set-firmware shim (Q9) is a separate audit-gated lift.
11. **`agent-installed` checkpoint is the M1 exit criterion.**
    Same checkpoint label `provisionVM` produces today. Re-use,
    don't introduce a parallel name.
12. **`b0ec24c`'s `withGuestCredentials` clone is the
    credential-routing primitive.** Every `vm exec` / `vm
    copy-file` step in the new pipeline goes through
    `orchestrator.backendForVm(vmName)` to pick up the scoped
    backend. No new credential plumbing.
13. **One verb, one binary.** No new MCP tool surface in M1 —
    the verb registers through the existing `loom.signalman.run`
    handler when invoked from a scenario. A standalone
    `loom.signalman.bootstrap_win11` MCP tool can land in M3 if
    needed.
14. **Test-signing certificate is an operator input, not a
    pipeline-generated artifact.** Operator supplies via
    `SIGNALMAN_TEST_SIGNING_CERT` env var or `--cert <path>` on
    the verb. The pipeline does NOT generate, fetch, or rotate
    the cert. v0.6 may add a generate-and-cache helper.

## Open decisions (M0 gate — block on operator answers)

1. **Q1 (testsigning persistence).** Is `bcdedit /set
   testsigning On` left set for the lifetime of the VM, or
   reverted after the MSI install in the same pipeline? If
   reverted: the test-signed driver won't survive reboots.
   Default rec: **leave testsigning on** for the demo VM's
   lifetime; document the caveat. Operator decides.

   **Locked 2026-05-17:** leave testsigning on for the demo VM's lifetime; document the caveat.
2. **Q2 (signed-MSI source).** Does the pipeline accept a
   pre-signed MSI only, or does it shell out to WS9 inline?
   Default rec: **pre-signed only in M1** (`--msi <path>` or
   `--msi-from-build <id>`); WS9 inline signing as a v0.6
   stretch. Operator decides.

   **Locked 2026-05-17:** pre-signed only in M1 (`--msi <path>` or `--msi-from-build <id>`); WS9 inline signing as a v0.6 stretch.
3. **Q3 (Secure Boot restore on teardown).** When the VM is
   destroyed, do we restore Secure Boot On as a
   defense-in-depth, or leave the template as-shipped?
   Default rec: **no restore** — the VM is destroyed anyway;
   Secure Boot state on a deleted VM is meaningless. But: if
   teardown is `--keep-vm` rather than `vm delete`, restore?
   Operator decides.

   **Locked 2026-05-17:** no restore — the VM is destroyed anyway; Secure Boot state on a deleted VM is meaningless. `--keep-vm` teardown likewise leaves Secure Boot Off; documented in M5 runbook.
4. **Q4 (cloud-init / Unattended.xml).** Does the pipeline
   drive first-boot config via an injected `Unattended.xml`
   (sysprep'd template, OOBE skip, admin auto-login), or does
   it boot a "manually-configured" template and only act
   post-boot? Default rec: **Unattended.xml-driven** — the
   template ships generalized, Unattended.xml supplies the
   per-VM hostname/admin/timezone. See M2 for details.

   **Locked 2026-05-17:** Unattended.xml-driven — template ships generalized; Unattended.xml supplies per-VM hostname/admin/timezone via M2 composer.
5. **Q5 (golden image strategy).** Where do the `win11-base`
   and `win11-dev` VHDXs come from? Default rec: **Packer
   manifest** under `examples/packer-win11/` that produces
   both — operator runs it once, output goes to a configurable
   library path. This is a separate workstream (Packer-WIN11),
   gated.

   **Locked 2026-05-17:** Packer manifest under `examples/packer-win11/` as a separate gated workstream (Packer-WIN11). M1 accepts operator-built VHDX via existing template paths.
6. **Q6 (libvirt parity timing).** Does M4 (libvirt
   set-firmware shim) gate the workstream, or does it ship
   v0.6 as a follow-up? Default rec: **M4 ships in this
   workstream** — without libvirt support, half the operator
   tree (Linux dev hosts) can't run the demo. Operator decides.

   **Locked 2026-05-17:** M4 ships in this workstream — Linux dev hosts must be able to run the demo.
7. **Q7 (bootstrap verb error envelope shape).** Same envelope
   shape as `signalman.run` (envelope_version, scenario_hash,
   etc.) or a slimmer bootstrap-specific shape? Default rec:
   **reuse the full envelope** — the pipeline IS a scenario
   internally; emitting the envelope keeps audit-log
   continuity. Operator decides.

   **Locked 2026-05-17:** reuse the full envelope shape — the pipeline IS a scenario internally; emitting the envelope keeps audit-log continuity.
8. **Q8 (concurrent bootstraps).** Two operators running
   bootstrap-win11 against different VMs at the same time —
   safe, or serialized? Default rec: **safe per-VM, serialized
   per-host** — guard with a `.signalman/state/locks/host.lock`
   file. Hyper-V tolerates parallel `Set-VMFirmware` on
   different VMs but parallel `Set-VMFirmware` on the same VM
   races (probably benignly, but no reason to find out).

   **Locked 2026-05-17:** safe per-VM, serialized per-host — guard with `.signalman/state/locks/host.lock` (advisory file lock, stale-pid-based unlock).
9. **Q9 (libvirt set-firmware semantics).** Hyper-V's
   `Set-VMFirmware -EnableSecureBoot Off` is one cmdlet.
   Libvirt's equivalent is editing the domain XML's
   `<loader>` + `<nvram>` lines + restarting the domain.
   Default rec: **shim via `virsh edit` + `virsh
   destroy`/`start` cycle** with idempotency check.
   Alternative: hot-reconfigure via `virsh nvram-define`
   without restart. Operator decides — affects M4 scope.

   **Locked 2026-05-17:** shim via XML edit + `virsh destroy`/`start` cycle with idempotency check. M4 work.
10. **Q10 (system-lane gating).** What env var gates the
    real-Win11 system lane? Default rec:
    `SIGNALMAN_WIN11_DEMO_TESTS=1` plus
    `SIGNALMAN_WIN11_TEMPLATE_VHDX=/path/to/win11-base.vhdx`
    plus `SIGNALMAN_TEST_SIGNING_CERT=...`. Mirrors the
    libvirt-parity `SIGNALMAN_LIBVIRT_TESTS=1` pattern.

    **Locked 2026-05-17:** `SIGNALMAN_WIN11_DEMO_TESTS=1` + `SIGNALMAN_WIN11_TEMPLATE_VHDX=...` + `SIGNALMAN_TEST_SIGNING_CERT=...`. Mirrors `SIGNALMAN_LIBVIRT_TESTS=1` pattern.

### M1: Hyper-V bootstrap verb (the meat)

- New file: `host/src/provisioning/bootstrap-win11.ts`. Exports
  `bootstrapWin11(opts: BootstrapWin11Opts): Promise<…>`.
  Twelve-step pipeline:
  1. Resolve template (reuse `templates.ts`).
  2. Acquire host lock (Q8) — `.signalman/state/locks/host.lock`.
  3. Read or create VM (idempotent — re-uses `provisionVM`'s
     create-VM step if VM doesn't exist).
  4. Read or set firmware: Secure Boot Off via
     `backend.setVmFirmware` (idempotent).
  5. Boot, wait for heartbeat (existing waitForHeartbeat).
  6. Stage certs (reuse `provisionVM` step 4).
  7. Run `bcdedit /set testsigning On` via the scoped backend
     (`backendForVm(name)`).
  8. Reboot VM, wait for heartbeat.
  9. Verify testsigning is On — `bcdedit /enum {current}` parse
     check.
  10. Resolve signed-MSI source (`--msi` or
      `--msi-from-build`).
  11. Copy + silent-install the MSI (reuse `provisionVM` step
      6).
  12. Checkpoint at `agent-installed`.
- New CLI verb: `signalman vm bootstrap-win11 <name>
  [--template …] [--msi …] [--cert …] [--cleanup-on-failure]
  [--force]`.
- New state file shape:
  `.signalman/state/bootstrap-win11/<vm-name>.json` —
  `{phase, lastCheckpoint, firmwareSet, testsigningOn,
  msiInstalled, agentInstalledCheckpoint}`.
- Existing verbs called: `vm set-firmware`, `vm create`,
  `vm start`, `vm wait-heartbeat`, `vm copy-file`, `vm exec`,
  `vm checkpoint`.
- Tests:
  - `bootstrap-win11.test.ts` — 25–35 unit tests covering
    every phase + idempotency + failure paths.
  - `bootstrap-win11-cli.test.ts` — argv parser tests.
  - One scenario fixture at `examples/bootstrap-win11/
    setup.yaml` for the system lane.
- Audit lens emphasis: **Architecture** (does the pipeline
  cleanly extend `provisionVM` rather than fork? does
  resumability cleanly compose with idempotency?).
- Verification gate: system lane against a real Win11 VM when
  `SIGNALMAN_WIN11_DEMO_TESTS=1` (Q10).

**Commit:** `feat(v0.5-win11-deploy): bootstrap-win11 verb +
12-step pipeline (Hyper-V)`.

## Test plan

### Unit lane (always-on)

- `bootstrap-win11.test.ts` — every pipeline phase, with
  injected backend stubs (existing pattern from
  `provision.test.ts`). Cover:
  - Idempotency: phase N is a no-op when state file says
    phase N already done.
  - Resume: pipeline run with state file at phase 5 starts
    at phase 5, not phase 1.
  - Failure mid-pipeline leaves state file at the failed
    phase (for next-run resume).
  - `--force` ignores state file, restarts from phase 1.
  - Each phase's individual failure surface — wrong creds,
    wrong template, missing MSI, signed-MSI rejected by
    Windows installer, reboot timeout.
- `bootstrap-win11-cli.test.ts` — argv parser, including
  flag aliases + invalid combinations.
- `unattended.test.ts` — XML composer round-trips, character
  escaping (admin password with `<`, `>`, `&`), encoding
  selection (UTF-8 with BOM per Microsoft spec).

### Integration lane (CI, in-process VM mocks)

- `bootstrap-win11-integration.test.ts` — full pipeline with
  a mock Hyper-V backend that simulates state transitions.
  Covers phase orchestration, event emission, envelope shape.

### System lane (gated, manual)

- `bootstrap-win11-system.test.ts` — drives a real Hyper-V
  Win11 VM when `SIGNALMAN_WIN11_DEMO_TESTS=1`. Asserts
  end-to-end success + checkpoint creation.
- `bootstrap-win11-libvirt-system.test.ts` — same but
  libvirt-backed. Gated additionally on
  `SIGNALMAN_WIN11_BACKEND=libvirt`.

### Coverage targets

## Risks + mitigations

| Risk | Mitigation |
|---|---|
| Win11 ISO licensing — can we ship a `win11-base.vhdx` in the repo? | **No.** Operator builds locally via Packer-WIN11. Repo ships the manifest, not the VHDX. |
| Test-signing certificate management is non-trivial — store, rotation, revocation | M1 punts to "operator-supplied via env var". M3 ships a runbook. v0.6 may automate. |
| Secure Boot Off + testsigning On reduces VM integrity guarantees | This is *the point* of the demo pipeline. Pipeline output is clearly labelled "test VM" in scenario envelope. Operator runbook documents the boundary. |
| Hyper-V Integration Services version drift across Win11 builds | Pin to a known-good build in the template (e.g. 23H2). Document in runbook. |
| Libvirt Win11 boot via UEFI + TPM + SMM is finicky (libvirt-multios audit flagged this) | M4 system lane gates on a known-good Packer artifact. Document the operator host requirements (OVMF firmware, swtpm). |
| Concurrent bootstraps race on `Set-VMFirmware` | Q8 — host-level lock under `.signalman/state/locks/host.lock`. |
| `Unattended.xml` exposes the local-admin password on the seed ISO | Seed ISO is mounted only at first boot; the bootstrap verb detaches + destroys the seed image after sysprep completes. Document. |

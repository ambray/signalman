## Problem statement

After M3, the registry hosts five facades: cargo + npm + OCI +
PyPI + Maven + NuGet. Each handles small-to-medium content-
addressed blobs (KB–MB per upload). HuggingFace is structurally
different:

- **Blob sizes are multi-GB** — model weights, tokenizers,
  datasets. A single repo can carry 50 GB across 20 files.
- **The protocol uses Git LFS** — clients clone a tiny pointer
  file from the HTTP-Git surface, then resolve LFS pointers
  to actual bytes via the LFS Batch API on a sibling endpoint.
- **Per-file revisioning** — a model has a revision SHA (Git
  commit SHA-1) that pins the entire tree; individual file
  versions don't exist outside the tree.
- **Bearer-token auth in the wild** — both `hf.co` itself and
  enterprise mirrors (HF Spaces self-hosted, Cloudflare R2-backed
  enterprise mirrors) authenticate via Bearer.

This facade lets a signalman operator stand up a registry that:

- Serves `huggingface-cli download <org>/<model>` against
  local content for cached models.
- Pulls through `huggingface.co` (or any HF-compatible mirror)
  for cache misses, with operator-supplied Bearer auth.
- Accepts operator uploads of a flattened tarball per model
  (the M0-locked "flattened, not full git push" path).
- Pins revisions on read so a model snapshot is reproducible.

End-state: `huggingface-cli download <org>/<model>
--revision <rev>` against the registry returns the same bytes
as against hf.co, with operator-controlled provenance + audit
trail + virtual-upstream pull-through caching.

## Goals

1. **Read surface: HF protocol parity for `download`.** The
   common workflows the WS13 prompt lists — `huggingface-cli
   download` of a small model — work against the registry
   end-to-end.
2. **LFS Batch API.** The protocol critical path: clients hit
   `/api/<repo_type>s/<org>/<repo>/lfs/objects/batch` to convert
   pointer files (~120 bytes of metadata) into HTTP URLs for
   the actual blob bytes. Without this, `download` 404s on
   every non-trivial file.
3. **Revision pinning.** Per-revision file-tree manifests so a
   `revision=v1.2.3` GET deterministically returns the same
   file set + bytes. Stored as a new `hf_revision` table.
4. **Multi-GB blob handling.** Content-addressed dedup at the
   registry's existing blob layer; streaming reads (no
   in-memory buffering of full blobs); HTTP Range requests on
   GET; chunked-upload state machine on operator push.
5. **Virtual upstream pull-through.** `huggingface.co` is the
   canonical upstream; private repos authenticate via
   `auth_header_template: 'Bearer <token>'`. The existing
   resign-on-cache + audit-log surface applies.
6. **Flattened operator publish (M0 lock).** Operator uploads
   a tarball per model; the registry unpacks it into per-file
   blobs + a revision row. **Not** a full `git push`; that's
   v0.7 stretch per the WS13 prompt.
7. **80% coverage gate per story.** Lines AND branches.
8. **4-lens audit at M4 close.**

## Non-goals

- **Full git push / clone protocol.** Operators use the
  flattened upload; full git protocol is v0.7+ stretch per the
  WS13 prompt.
- **HF Spaces / Datasets push.** Read of `dataset` and `space`
  repo types is supported; publish is models only in M4.
- **Discussion / community features.** No PRs / discussions /
  comments surface.
- **Diffusers / Transformers SDK preference negotiation.** We
  serve the canonical HF protocol; SDK quirks are the
  consuming client's problem.
- **Server-side model conversion.** No safetensors ↔ pytorch
  ↔ GGUF transforms.
- **End-to-end encryption / DRM.** Out of scope.
- **HF Inference Endpoints proxy.** Not a registry concern.

## Locked design

Inferred from the existing facade pattern (cargo/npm/OCI/PyPI/
Maven) + HF Hub API documentation
(`huggingface.co/docs/hub/api`) + Git LFS Batch API spec.
Confirm at M0 gate; agent auto-locks defaults unless code
review surfaces a contradiction.

1. **Storage manifest names: `hf/<org>/<repo>/<repo_type>`**
   where `<repo_type>` is `model` (default) / `dataset` / `space`.
   Per-row version is the filename, mirroring PyPI / Maven.
2. **Revision rows live in a new `hf_revision` table** —
   `(org, repo, repo_type, revision, root_tree_digest, parent_revision?, created_at, files_json)`.
   Files are stored as a JSON list of `{path, sha256, size, lfs?: boolean}`. The root_tree_digest is the SHA-1 of the canonical tree shape (matches what git would emit) so it round-trips with the HF UI's commit-shaped revisions.
3. **Two read surfaces:**
   - **HTTP-Git proxy lane** —
     `/hf/<org>/<repo>/resolve/<revision>/<path>` returns the
     bytes (or, for LFS-tracked files, returns the pointer
     file). Mirrors `https://huggingface.co/<org>/<repo>/
     resolve/<revision>/<path>` byte-for-byte.
   - **LFS Batch API** —
     `/hf/<org>/<repo>/info/lfs/objects/batch` (POST). Accepts
     `{operation: 'download', objects: [{oid, size}]}` and
     returns `{objects: [{oid, size, actions: {download:
     {href, header?}}}]}`. The `href` points at our blob
     content-addressed endpoint.
4. **Blob-bytes endpoint:** `/hf/<org>/<repo>/lfs/sha256/<sha256>`.
   HTTP Range supported. ETag = `sha256:<hex>`. The LFS Batch
   `href` always points here.
5. **Publish endpoint:**
   `POST /hf/<org>/<repo>/upload-tarball?revision=<rev>` with
   `Content-Type: application/x-tar` (or
   `application/octet-stream`, gzipped acceptable via
   `Content-Encoding: gzip`). Body is a flat tar of the model's
   file tree. The server streams the tar, content-addresses
   each file's bytes, writes a revision row, and returns
   `{revision, file_count, total_bytes}`.
6. **Max blob size:** 50 GB hard cap. Operator-overridable per
   org via virtual_upstream config. Streaming end-to-end (no
   in-memory accumulation of the full tar).
7. **Revisions are append-only.** Same `revision` ID with
   different files is 409 CONFLICT. Operators rotate via a
   new revision string.
8. **Default revision = `main`** — clients omitting
   `revision` get the latest `main`. Stored as a sentinel row
   with `revision = 'main'`; each publish updates the row to
   point at the just-uploaded files.
9. **Pull-through cache hooks:**
   - `proxyHfModelMetadata(org, repo, repo_type)` — fetches the
     upstream model page metadata + revision list when no local
     rows exist for the repo.
   - `proxyHfResolve(org, repo, revision, path)` — on a
     `/resolve/<revision>/<path>` miss, fetches the upstream
     path. For LFS-tracked files this means: fetch the pointer
     from the upstream Git side, then translate the OID via
     upstream LFS Batch, then stream the actual bytes from the
     upstream LFS provider.
   - `proxyHfLfsBatch(org, repo, oids[])` — on a Batch request
     against unknown OIDs, calls the upstream Batch API,
     translates the response so the `href` fields point back
     at our local cache endpoints, and (lazily, on first GET
     of each `href`) hydrates the bytes.
10. **Upstream auth:** `Authorization: Bearer <token>` via
    `auth_header_template`. The HF UI / `huggingface-cli`
    token-helper file is **not** read server-side — operators
    plumb the token into the upstream config.
11. **Audit-log actions:** `upload` for publish-tarball;
    `proxy_cache` for any pull-through with
    `phase: 'metadata' | 'resolve' | 'lfs_batch' | 'blob_bytes'`.
12. **Manifest media type:** `application/vnd.signalman.hf-file.v1+json`
    on per-file manifest rows; the revision rows use
    `application/vnd.signalman.hf-revision.v1+json` and live
    in a sibling SQLite table (not `manifest`) because they
    don't carry blob references directly (the files do).

## Open decisions (M0 gate — auto-lock defaults)

Procedure: open this doc, append `**Locked 2026-05-17:** <default>` inline under each Q, then commit `docs(v0.6-multi-ecosystem): lock M4 defaults`.

1. **Q1 — Per-blob 50 GB cap.** Hard cap with explicit error,
   or operator-config-override? **Default rec:** hard cap +
   override knob `hf_max_blob_bytes` on the virtual_upstream
   config row.
2. **Q2 — LFS Batch authentication forwarding.** When the
   upstream is private (Bearer), do we forward the operator's
   token in the `download` action's `header.Authorization`
   block (so the client fetches directly upstream-via-the-
   header), or fully proxy through us (the action `href`
   points at our cache endpoint, we fetch upstream with our
   token)? **Default rec:** fully proxy. Cleaner audit trail;
   client never sees the upstream token.
3. **Q3 — Chunked upload state machine.** Single-shot
   `POST upload-tarball` (simpler, fails on the entire upload
   for any network blip on a multi-GB push) vs chunked-upload
   protocol (resumable, more code). **Default rec:** single-
   shot in M4. Chunked upload lands as M4.1 if operators
   request it. Document the trade-off in the audit doc.
4. **Q4 — Revision retention.** Keep all revisions forever
   vs operator-configurable retention (e.g. last 50 revisions
   per repo)? **Default rec:** keep all in M4; add a `prune
   revisions older than N` admin verb in v0.7. Audit-log
   surface is the operator-visible safety net.
5. **Q5 — Symlink / submodule handling in operator tarballs.**
   Reject the upload, follow the symlink, store verbatim?
   **Default rec:** reject — fail the upload with
   `UPLOAD_INVALID` for any tar entry that's not a regular file
   or directory. Operators who need submodules use the v0.7
   git-push path.
6. **Q6 — Default revision string.** `main` (matches GitHub /
   HF UI), `master`, `latest`? **Default rec:** `main`.
7. **Q7 — Cache miss → upstream 404 propagation.** When the
   client requests a revision that doesn't exist locally and
   doesn't exist upstream either, 404 with HF's spec body
   `{error: 'Repository not found', ...}` or our generic
   error envelope? **Default rec:** HF-canonical 404 body
   (`huggingface-cli` parses it).
8. **Q8 — `hf_revision` table primary key.** Composite
   `(org, repo, repo_type, revision)` or surrogate UUID?
   **Default rec:** composite — easier to query / migrate;
   matches manifest table's compound-key convention.

### Story 4 — Publish: flattened tarball upload + revision row

- New file: `registry/src/hf/publish.ts`.
  - `POST /hf/:org/:repo/upload-tarball?revision=<rev>`.
  - Streaming tar parser (use `tar` from npm if already a
    dep; otherwise `tar-stream`; otherwise hand-roll the
    parsing for the small grammar we need — confirm against
    package.json before adding a dep, per Selvedge convention).
    Hand-rolled is acceptable: tar's USTAR header is 512 bytes
    + payload + padding-to-512.
  - For each entry: reject non-regular-files (Q5 default);
    content-address via `storage.putBlob`; collect into the
    files-list.
  - On end: write `hf_revision` row + per-file manifest rows
    (each `kind: 'hf'` with `hfMetadata.path / sha256 / size /
    lfs` set; `lfs: true` for files > 5 MB by default — the
    HF convention).
  - 409 on revision-already-exists.
- Tests: `hf-publish.test.ts` (~20 tests: happy path, 409
  conflict, malformed tar, symlink rejection, oversize blob
  rejection, idempotent same-bytes re-upload).
- **Coverage gate: ≥80%/80%**.

## Risks + mitigations

| Risk | Mitigation |
|---|---|
| Multi-GB tar parsing OOMs on naive impl | Streaming end-to-end; never accumulate full file into memory; verify with a 1 GB test fixture (skipped on CI; gated locally) |
| LFS Batch response shape drift from HF spec | Pin to the documented schema; integration test asserts the exact JSON shape `huggingface-cli` expects |
| Revision IDs that look like Git SHAs but aren't (operator-supplied) | Validate as `^[A-Za-z0-9._-]{1,64}$` — accept any meaningful tag/branch name; don't require SHA-shaped |
| Pull-through fetches a multi-GB blob the operator didn't intend | Audit-log `proxy_cache` with `bytes_fetched`; operator can configure `deny_patterns` to refuse large pull-through; default 50 GB hard cap |
| HF Bearer token leaks via error message or audit log | Token redacted in error envelopes + audit detail (mirror the pattern used for cargo virtual auth) |
| Symlink in tarball points outside the model dir | Story 4 rejects all non-regular-file tar entries up front |

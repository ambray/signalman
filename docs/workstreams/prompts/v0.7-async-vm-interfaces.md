## Why this workstream exists

The v0.6 KVM provisioning workstream (closed 2026-05-18) surfaced
direct evidence that signalman's current request-response interfaces
collapse for long-running VM operations:

- `VMProvisioner.runPipeline` blocks for 45-60 min during `wait_installer_complete`. If the calling process is killed mid-wait, the wait dies even when the underlying install continues. We worked around this with `nohup` + watchers + manual recovery; the fragility was operator-visible.
- `LibvirtBackend.executeCommand` (via QGA) blocks until the guest command exits. A 20-30 min VS Build Tools install would hold the caller for the full duration.
- `LibvirtBackend.copyFileToVM` for multi-MB payloads streams synchronously. If the caller process dies mid-copy, partial state is left on the guest.
- `TemplateManager.fetch` blocks for multi-GB ISO downloads. We got lucky with SHA-pinned cache resume; correctness was not load-bearing on a retry pattern, but it was close.
- `AgentInstallManager.installIntoGuest` runs `msiexec` / `apt install` synchronously. Same shape, same fragility.

The pattern is clear: anything that runs for longer than ~30s should be a **job**, not a blocking RPC. Caller submits, daemon owns the work, caller polls or subscribes for status. This is the same shape as the existing release-deployment ledger in `host/src/control-plane/` (release builds have IDs, status, history) — Wave B extends that pattern to VM operations.

## What success looks like

After Wave B closes:

- `signalman vm provision <name> --template ... --no-wait` returns immediately with a `JobID`. The pipeline runs inside the daemon (Windows service / Linux privhelper). The CLI process can exit; the work continues.
- `signalman jobs status <job-id>` reports the current phase + percent-complete + last-updated timestamp.
- `signalman jobs subscribe <job-id>` streams events; an agent or operator can survive disconnects and reconnect to the same stream.
- `signalman vm provision <name> --template ... --wait` (the **default**, back-compat) submits a job + waits + reports events to stdout. Existing operators see no behavior change.
- A daemon restart does not lose in-flight jobs. The job ledger is persisted to SQLite (same storage layer the meta-build catalog uses).
- Every existing manager interface (`HypervisorBackend`, `TemplateManager`, `ProvisioningManager`, `AgentInstallManager`) grows a job-submission shape alongside its existing methods. Existing fast ops (`list`, `getStatus`, `dumpXml`) stay request-response.

This is the foundation that unblocks:

- Wave C — Linux privhelper daemon (will host jobs from day one).
- Wave D — `BuildHostManager` workstream (long-running build-tool installs as jobs).
- Wave E — self-bootstrap (depends on B + C + D).

## Locked decisions

The operator authorized these defaults at workstream design time
(2026-05-18). The agent locks them as **Locked 2026-05-18** in the
design doc and proceeds.

1. **Job storage = SQLite, sibling table to the release catalog.** Same storage driver, same connection pooling, same backup story. Migration block: 0050-0059 reserved for v0.7 (verify against `host/src/control-plane/storage/migrations/` for conflicts at M0).
2. **Job IDs = ULID** (lexicographically sortable + time-encoded). Mirror the existing `release_id` pattern.
3. **Authentication for daemon RPCs:** Windows service keeps existing mTLS; Linux privhelper (Wave C) uses Unix socket + SO_PEERCRED. The job-submission API spec is identical on both.
4. **Subscription wire protocol:** Server-Sent Events (SSE) over the existing transport. Each `JobEvent` is a JSON object on a single line. Reconnect-by-job-ID is supported (the daemon replays missed events from the SQLite log up to `lastEventId`).
5. **Backwards compatibility:** every existing CLI verb keeps working unchanged. `--wait` (the new default) preserves the synchronous experience. `--no-wait` is the opt-in.
6. **Job kinds**: fixed enum in the schema (`vm_create`, `vm_start`, `vm_stop`, `vm_create_install`, `vm_wait_installer`, `vm_wait_guest_ready`, `template_fetch`, `template_prepare`, `agent_resolve`, `agent_install`, `setup_complete_wait`). New kinds are added by schema migration, not by string-typing.
7. **Job event payloads:** typed per `JobKind` via discriminated union. No `extra: Record<string, unknown>` escape hatch.
8. **Audit-log integration:** every job state transition emits one row to the existing audit log table (`host/src/control-plane/storage/migrations/0021_audit.sql` or similar — verify at M0). Wave B is the consumer of the existing audit infrastructure, not a creator.
9. **Timeout policy:** every job has an `operator_timeout_ms` (when the operator wants the job to fail-and-give-up) + an `infra_timeout_ms` (when the daemon decides the job is stuck regardless of operator preference). Defaults per kind; explicit overrides allowed.
10. **Cancellation:** every job is cancellable. `cancelJob` triggers cleanup-specific shutdown (e.g. for a `template_fetch` in flight: close the HTTP stream + delete partial file). Cancellation is best-effort + recorded in the job result.

### Story 5 — VMProvisioner phase reshape

- Each of the 15 phases in `host/src/provisioning/vm-provisioner.ts`
  becomes a job submission.
- Phase ordering = job dependencies (the orchestrator only submits
  phase N+1 after phase N succeeds).
- The state journal becomes the orchestrator's view onto job IDs +
  their statuses, not phase-name + completion-timestamp.
- Crash recovery: re-read the orchestrator's job-tracking map +
  reconnect to JobStore subscription.

Tests: full pipeline runs end-to-end as job-orchestrated; crash recovery
preserves in-flight job tracking; cancellation cancels the entire
pipeline + cleans up VM state.

Commit: `feat(v0.7-async-vm-interfaces): VMProvisioner phases as jobs + recovery`.

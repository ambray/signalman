# Server Silo Validation — Workflow

> **Narrator**: This workflow validates that Windows Server Silo kernel APIs
> are available and functional on the target endpoint. Silos are the kernel
> primitive underlying Windows containers and are required for Ospiri's
> sandbox enforcement mode. Each step exercises a specific aspect of silo
> behaviour.

## Prerequisites

The `setup.yaml` has already:
- Provisioned a Windows 11 VM (`endpoint-1`)
- Restored the `agent-installed` checkpoint

## Step 1: Deploy Silo Validation Binary

Copy the pre-built `silo-validation.exe` tool into the VM. This binary
exercises ntdll silo APIs without requiring container infrastructure.

```tool
vm_copy_file:
  vm: endpoint-1
  src: ./artifacts/silo-validation.exe
  dest: "C:\\Ospiri\\tools\\silo-validation.exe"
```

Verify the binary is in place:

```tool
vm_run_command:
  vm: endpoint-1
  command: powershell
  args: ["-Command", "Test-Path 'C:\\Ospiri\\tools\\silo-validation.exe'"]
  expect_stdout: "True"
```

## Step 2: Run Full Validation Suite

Execute the validation binary with `--all` to run every test. Results are
written to a JSON file for machine-readable assertion checking.

```tool
vm_run_command:
  vm: endpoint-1
  command: "C:\\Ospiri\\tools\\silo-validation.exe"
  args: ["--all", "--output", "C:\\Ospiri\\logs\\silo-results.json"]
  timeout_ms: 120000
```

The binary should exit with code 0 if the suite completed (individual tests
may fail; the exit code reflects whether the harness itself ran successfully).

## Step 3: Retrieve Results JSON

Copy the results file back to the host for assertion evaluation.

```tool
vm_copy_file:
  vm: endpoint-1
  src: "C:\\Ospiri\\logs\\silo-results.json"
  dest: ./results/silo-results.json
  direction: from_vm
```

Inspect the summary:

```tool
vm_run_command:
  vm: endpoint-1
  command: powershell
  args: ["-Command", "Get-Content 'C:\\Ospiri\\logs\\silo-results.json' | ConvertFrom-Json | Select-Object -ExpandProperty summary | Format-List"]
```

## Step 4: Validate Silo APIs Are Available

Check that the ntdll silo APIs (`NtCreateServerSilo`, `NtTerminateServerSilo`,
`NtAssignProcessToServerSilo`, etc.) are exported and callable on this
Windows build. If these APIs are missing, the OS version does not support
silos at all.

```tool
vm_run_command:
  vm: endpoint-1
  command: powershell
  args: ["-Command", "Get-Content 'C:\\Ospiri\\logs\\silo-results.json' | ConvertFrom-Json | Select-Object -ExpandProperty summary | Select-Object -ExpandProperty silo_apis_available"]
```

The output should be `True`. If `False`, silos are not supported on this
Windows build and all subsequent steps are expected to fail.

## Step 5: Check Process Assignment Behaviour

Verify that a suspended process can be assigned to a silo before it begins
executing. This is the mechanism Ospiri uses to sandbox a newly launched
application: create the process suspended, assign to silo, then resume.

```tool
vm_run_command:
  vm: endpoint-1
  command: powershell
  args: ["-Command", "Get-Content 'C:\\Ospiri\\logs\\silo-results.json' | ConvertFrom-Json | Select-Object -ExpandProperty tests | Where-Object { $_.name -like '*assign*suspended*' } | Format-List"]
```

The test should show `result: pass`. If it shows `result: fail`, the
suspended-process assignment path may not work on this build.

Also check the running-process assignment test (expected to fail on most
builds, since Windows restricts silo assignment to suspended processes):

```tool
vm_run_command:
  vm: endpoint-1
  command: powershell
  args: ["-Command", "Get-Content 'C:\\Ospiri\\logs\\silo-results.json' | ConvertFrom-Json | Select-Object -ExpandProperty tests | Where-Object { $_.name -like '*assign*running*' } | Format-List"]
```

## Step 6: Check Handle Close Behaviour

Verify that handles opened by a silo'd process are properly isolated and
that closing the silo terminates or orphans those handles correctly. This
is important for preventing resource leaks when Ospiri terminates a sandbox.

```tool
vm_run_command:
  vm: endpoint-1
  command: powershell
  args: ["-Command", "Get-Content 'C:\\Ospiri\\logs\\silo-results.json' | ConvertFrom-Json | Select-Object -ExpandProperty tests | Where-Object { $_.name -like '*handle*' } | Format-List"]
```

## Step 7: Check ETW Visibility from Silo'd Processes

Verify that ETW events generated by processes inside a silo are still
visible to the host-level ETW session. This is critical for Ospiri's
telemetry pipeline: even sandboxed processes must be observable.

```tool
vm_run_command:
  vm: endpoint-1
  command: powershell
  args: ["-Command", "Get-Content 'C:\\Ospiri\\logs\\silo-results.json' | ConvertFrom-Json | Select-Object -ExpandProperty tests | Where-Object { $_.name -like '*etw*' } | Format-List"]
```

If the ETW visibility test fails, Ospiri may need to run a secondary ETW
session inside the silo or use an alternative telemetry path.

## Step 8: Check AppContainer + Silo Composition

Verify that an AppContainer token can coexist with a silo assignment. This
composition is the basis of Ospiri's full sandbox: network isolation via
AppContainer + process namespace isolation via silo.

```tool
vm_run_command:
  vm: endpoint-1
  command: powershell
  args: ["-Command", "Get-Content 'C:\\Ospiri\\logs\\silo-results.json' | ConvertFrom-Json | Select-Object -ExpandProperty tests | Where-Object { $_.name -like '*appcontainer*silo*compose*' } | Format-List"]
```

The composition test (`P1-appcontainer-silo-compose`) must have run. If it
passed, the full sandbox model is viable on this Windows build.

## Expected Outcomes

| Check | Expected |
|-------|----------|
| Silo APIs available | `True` on Windows 11 22H2+ and Server 2022+ |
| Assign suspended process | `pass` |
| Assign running process | `fail` (expected; Windows restricts this) |
| Handle isolation | `pass` |
| ETW visibility | `pass` |
| AppContainer + Silo composition | `pass` (must have run) |
| Overall pass rate | >= 6 of total tests pass |
| Errors | 0 crashes or exceptions |
